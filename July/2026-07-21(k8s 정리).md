### Kubernetes (K8S)
- 해당 기술의 전체적인 그림은 아래와 같음.
![alt text](image-5.png)

- 여러 물리적이고 논리적인 서버를 한번에 관리하기 위한 애플리케이션임. 
  - 1차적으로 물리적인 서버로 나눔
  - 2차적으로 논리적인 서버로 나눔

#### 쿠버네티스 사용 이유
1. Pod를 자동으로 생성, 수정, 삭제
    - 서버의 자원을 전체적으로 파악해서 남는 자원이 있으면 해당 위치에 pod를 생성함.
    - 특정 pod가 에러나서 동작을 멈추면, 자동으로 재시작할 수 있도록 제어함.
    - 필요한 처리량에 따라서 자동으로 Auto-Scaling 가능
    - 롤링 업데이트 지원함.
2. 클러스터와 Pod 내의 자원 사용량을 실시간으로 모니터링 
    - 옵저빌리티 기능 제공으로 중앙에서 관리해서 운영이 편해짐. 

#### 컨테이너 오케스트레이션
- 여러 서버에서 실행되는 많은 컨테이너를 생성, 수정, 삭제 등을 자동화 하는 것.
    - Docker: 컨테이너를 만들고 실행하는 도구
    - Kubernete: 여러 서버에서 많은 Pod를 관리하는 도구

#### Kubernetes의 특징
##### 1. 선언적 관리
- 지금까지 해왔던 작업은 운영자가 서버에 접속해서 명령어로 관리하는 것이였음. 하지만 k8s는 운영자가 최종적으로 원하는 상태를 정의해서 관리함 -> 선언적 관리

##### 2. Desired State
- 선언적 관리와 비슷한 말. 사용자가 k8s에게 원하는 상태를 전달하여 명령하는 것
- 쿠버네티스에서 **원하는 상태와 현재 상태를 지속적으로 비교**하여 원하는 상태가 되도록 계속 자동적으로 제어함.

### k8s 요소
#### 1. 클러스터
- 쿠버네티스가 관리하는 여러 서버, 컨테이너, 리소스의 집합
    ```
    Kubernetes Cluster
    ├── Control Plane
    ├── Worker Node 1
    ├── Worker Node 2
    └── Worker Node 3
    ```
    - 클러스터를 구성하는 각 서버는 모두 `Node`라고 부름.
    - `Node`는 물리서버, 가상 머신, 온프레미스 서버 등이 될 수 있음.
    - 일반적으로 클러스터를 구성할 때는 노드의 구성을 하나로 통일하려는 경향이 있음. -> 물리서버, 가상 머신 등을 모두 Node로 할 수 있게 하면 종류가 여러개여서 운영 복잡도가 올라감.

#### 2. Control Plane(Master Node)
- 클러스터 전체의 상태를 관리하고, `Pod`배치를 판단하는 중앙 제어 영역
- 구성
    ```
    Control Plane
    ├── kube-apiserver
    ├── etcd
    ├── kube-scheduler
    └── kube-controller-manager
    ```

##### 1. kube-api-server
- 클러스터로 들어오는 모든 관리 요청의 중앙 출입구
- 사용자가 kubectl 명령어를 내리면, 워커 노드에 직접 전달 되지 않고 API Server에 전달되고 그 후에 워커 노드로 전달됨.
- 역할
    1. 사용자 요청 수신
    2. 사용자 인증 및 권한 확인
    3. 내부 구성 요소간 통신 중계
    4. 클러스터의 상태 변경 및 조회 -> etcd

##### 2. etcd
- 클러스터의 설정과 상태를 저장하는 **분산 key-value 저장소**
- 운영 환경에서는 etcd가 매우 중요해서 백업, 다중화, 복구 작업 준비, 접근 제한 등 가용성과 보안성이 높아야함.

##### 3. kube-scheduler
- Pod를 어느 worker node에 배치할지 결정하는 구성요소
- 고려사항
    1. Node의 CPU, Mem 등의 자원
    2. Pod에서 요청한 자원
    3. 설정한 배치 조건
- Pod를 실행할 Node를 결정하기만 하고 실행까지 담당하지는 않음.

##### 4. kube-controller-manager
- 현재 상태를 사용자가 원하는 상태로 맞추도록 여러 제어 기능을 실행하는 구성 요소
- 흐름 순서
    1. etcd에 있는 현재 상태와 원하는 상태 비교
    2. kube-controler-manager이 다름을 감지
    3. 부족한 실행단위를 생성 요청

#### 3. Worker Node
- 실제 Pod가 실행되는 서버
- `Control Plane`이 두뇌면 워커노드는 작업을 수행하는 손과 발 느낌
- 구성
    ```text
    Worker Node
    ├── kubelet
    ├── Container Runtime
    ├── kube-proxy
    └── 애플리케이션 실행 단위
    ```
- 역할 
    1. 컨테이너 이미지 다운로드 및 실행
    2. 컨테이너 상태 확인 및 장애 대처
    3. 네트워크 통신 처리

##### 1. kubelet 
- 각 worker node에서 pod 실행 상태 관리 및 Controller Plane에 보고하는 구성 요소
- 역할
    1. API Server와 통신을 통한 실행해야하는 작업 확인
    2. `Container Runtime`에 작업 요청
    3. 컨테이너 상태 확인
