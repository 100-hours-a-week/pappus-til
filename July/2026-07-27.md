### RBAC 
- Role-Based Access Control
- 쿠버네티스에서는 많은 주체가 Kubernets API Server를 사용함.

#### RBAC가 없으면
1. 모든 사용자에게 관리자 권한을 주는 것임.
    - 오케스트레이션 툴이기에 CP에게 모든 권한을 부여 ( 과도한 권한을 가지고 있는 구조)
2. 네임스페이스 분리가 의미 없어짐.
3. 애플리케이션이 권한을 가짐.
    - PLG Stacke
      - 프로메테우스 + 로키 + 그라파나
        - 매트릭, 로그 중앙 집중형 수집 + 대시보드
    - 모니터링 툴은 많은 사람들이 사용하기에 
4. 권한을 사용자마다 개별 관리가 힘듦.

#### RBAC 동작방식
- Role: 어떤 작업을 허용할 것인가
- 
```
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: backend
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get","list","watch"]
```

- Binding: 그 권한을 누구에게 줄 것인가
```
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: bind-pod-reader
  namespace: backend
subjects:
  - kind: ServiceAccount
    name: backend-reader
    namespace: backend
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: pod-reader
```

### Service Account
- Pod같은 애플리케이션이 Kubernetes API를 사용할 때 사용하는 클러스터 내부의 신원

#### 사용방법

1. SA 생성
2. Role
3. RoleBinding
4. Pod에 연결

- Default Service Account: Pod에 ServiceAccount를 지정하지 않으면 Namespace의 default ServiceAccount를 사용함.

#### 실무
1. 애플리케이션별로 ServiceAccount 구성
2. defaultServiceAccount
3. 최소 권한 원칙 적용
4. 생성,삭제,수정 권한은 유의해서 사용.

### Helm
- 여러 k8s YAML 파일을 하나의 설치 패키지인 Chart로 묶고, 설정값만 바꿔 반복적으로 설치, 업데이트할 수 있게 해주는 K8s 패키지 관리자.

- dev, prod, feature, stag를 구분하는데 이를 구분하기 위한 yaml의 차이는 값밖에 없음. 형식은 거의 똑같거나 같음.
    - `반복되는 YAML 구조`: Template
    - `환경마다 바뀌는 값`: Values

#### 구조의 변경점
- Helm 사용 이전
```
express-app/
─ deployment.yaml
─ service.yaml
─ configmap.yaml
```

- Helm 사용 이후
```
express-chart/
├── Chart.yaml
├── values.yaml
└── templates/
    ├── deployment.yaml
    ├── service.yaml
    └── configmap.yaml
```

#### Chart
- 이름과 버전 같이 기본 정보를 작성하는 파일임.

```yaml
apiVersion: v2
name: express-app
description: Express application Helm chart
type: application
version: 0.1.0
appVersion: "1.0.0"
```

#### values 
- 여러 템플릿에서 사용할 변경되는 설정 값들이 있는 파일.

- 설정된 values.yaml
``` yaml
replicaCount: 2

image:
  repository: adapterz/k8s-pod
  tag: "1.0.0"
  pullPolicy: IfNotPresent

message: "Hello Kubernetes"

service:
  type: ClusterIP
  port: 80
  targetPort: 3000

resources:
  requests:
    cpu: 100m
    memory: 128Mi
  limits:
    cpu: 500m
    memory: 256Mi
```

- 위에 설정된 values값을 사용하는 template 예시
```yaml
spec:
  replicas: {{ .Values.replicaCount }} # 위의 replicaCount값 2를 가져옴  

```

#### templates
```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: {{ .Release.Name }}-config
data:
  MESSAGE: {{ .Values.message | quote }}
```

- 위는 아래와 같은 의미
```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: express-config
data:
  MESSAGE: "Hello Kubernetes"
```

#### 실무에서 사용하는 방식
1. 외부 운영 도구 설치
2. 애플리케이션 배포
3. Values에 변경되는 값만 넣기
4. Chart Repo는 안전한지 꼭 확인하고 설치
5. Github에 올라가는 파일이기에 평문으로 저장 X



### Ingress
- 클러스터 외부 HTTP,HTTPS 요청을 내부 Service로 연결하는 라우팅 규칙
- Ingress Controller: Ingress 규칙을 읽고 실제 요청을 전달하는 프로그램.

#### 사용 이유
- NodePort Service의 불편한 점.
1. 서비스마다 포트 관리하기에 열어둬야하는 포트가 늘어났음.
    - 이로써 공격지점이 넓었음.
2. 접속하려면 포트까지 입력해야했음.
3. HTTPS 설정이 분산됨.

#### Ingress 구조
```
                      ┌→ frontend-service → frontend Pod
사용자 → Ingress Controller
                      ├→ backend-service  → backend Pod
                      └→ admin-service    → admin Pod
```
- 외부에서는 80,443에 http,https로 요청함. (TCP, UDP는 안됨.)
- URL 기반의 라우팅 
  - **의문:** ALB랑 비슷한 듯? 왜 ALB를 사용하지 않고 내부적으로 Ingress라는 것을 만든 거지?
  - **의문해결:** AWS ALB랑 비슷하지만 ALB는 k8s안에 있는 것이 아니라 Service들을 알고 있지 않음. 그래서 사이에는 뭔가 있어야 하는데 그럼 AWS ALB를 사용한다는 가정하에 Ingress controller인 AWS Load Balancer Controller를 사용하게 되어서 어차피 Ingress controller를 사용해야함.

#### 동작 과정

```
1. 사용자가 Ingress YAML 생성
2. API Server가 Ingress 리소스 저장
3. Ingress Controller가 변경 감지
4. Controller가 라우팅 설정 생성
5. 외부 요청 수신
6. Host와 Path 확인
7. 대상 Service 또는 Endpoint로 전달
8. Pod가 요청 처리
```

#### Ingress Class
- 클러스터에는 여러 종류의 Ingress와 Ingress Controller가 있는데, 이때 어떤 컨트롤러가 특정 Ingress를 처리할지 지정할 때 사용함.

#### 실무
- 요즘은 API Gateway를 사용하는 것이 표준화되고 있음. 
- TCP,UDP까지 처리할 수 있음.

### 한줄 정리

- RBAC: AWS의 IAM같이 사용자의 권한을 제한하기 위해서 사용하는 것.
- Role: 규칙 
- Binding: 규칙 연결

- Default Service Account: 기본 service account, 아무것도 없을 때 사용할 기본적인 것
- User Account: 사람이 사용하는 인증, 클러스터 관리에 대한 권한을 제한하기 위해서.
- Helm: k8s의 전체적일 설정을 묶어서 관리할 수 있도록 하는 기술, 파일이 많아져서 유지/보수가 힘들어져서.
- Template: 반복되는 yaml 형식을 정형화하여 재사용하기 위해서 작성하는 것.
- values.yaml: 정형화된 template에 넣을 값들을 적는 곳, 값은 변경해야하니까?
- Chart: values, template 모두를 묶은 패키지 같은 것.
- Release: chart를 k8s 넣은 결과
- Ingress: 외부 요청을 내부에 어떻게 전달할지 정한 규칙,
- Ingress Controller: ingress를 실행하는 프로그램

### 의문

**Q: ingress를 사용하는 이유**
  - API Gateway가 HTTP,HTTPS,TCP,UDP 모두 처리할 수 있으니까 ingress 상위 호환이지 않는가? 
  - 소규모에서 비용적으로 ec2 하나만 사용하는 ingress가 더욱 저렴한 것인가? (하지만 k8s를 적용한 순간부터 이미 대규모 프로젝트인데...?)

A: ingress는 지금 봤을때는 API Gateway에 비해서 하위호완이다. 하지만 상대적으로 API Gateway보다 오래 사용했기에 안정성이 높다.
비용은 API Gateway와 ingress 비슷하다고 생각한다.

개인적인 생각: 시간의 흐름에 따라 기술이 발전하여 사라지는 기술을 우리가 공부하고 있는 것은 처음이라 신기했다. 항상 이론적으로 배울 때는 근본이 되는 기술을 배웠고 (network ALOHA), 기술적으로 배울 때는 최신기술을 배운 것 같은데, 사라져가는 기술은 처음이라 마이그래이션 할 때가 기대된다. 진짜 실무경험을 하는 것 같은 착각이 든다.

**Q: Service는 로드 밸런싱을 하는가?**

A: 그렇다. 정확히는 kube-proxy가 iptables proxy mode인 기본적으로 랜덤으로 endpoint에 패킷을 전달한다.

## 오늘의 회고
- 개인적으로 Service에 로드 밸런싱을 제공하는지 처음알았다. 분명 다른 팀원은 기억하고 있었는데 나는 기억하고 있지 못했다. 아마 내가 생각하는 로드밸런싱은 가중치 로드밸런싱만 생각해서 Random Load Balancing은 가치 없다고 생각하고 Service에 있다는 것을 중요하게 보지 않았던 것 같다. 
- 그러니 위의 문제는 Load balancing의 정확한 정의를 모르고 있어서 발생한 문제이다. 이는 실무에서 전문용어로 이야기하는 이유를 생각하면 고쳐야하는 부분인 것 같다. 지금까지는 대충 의미만 알면 되겠지라는 생각이였는데, 앞으로는 전문용어를 배우면 이에 대한 정의를 명확하게 가져가야겠다.
