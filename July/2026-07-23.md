## Volume
- 컨테이너의 파일 시스템을 확장하거나 공유하기 위해 사용되는 데이터 저장소

### 1.사용 이유
1. 컨테이너가 재시작 될 때 데이터를 유지
2. 파드 내부 컨테이너간 데이터 공유
3. 설정, Secret 파일로 전달

### 2.Volume YAML
```yaml
spec:
  containers:
    - name: app
      image: nginx
      volumeMounts:
        - name: app-data
          mountPath: /data

  volumes:
    - name: app-data
      emptyDir: {}
```

1. `Volums`: Pod를 사용할 공간을 정의하는 것
2. `volumeMounts`: 사용하는 불륨을 컨테이너의 어느 경로에서 사용할 지를 정의함

### 3.Volume의 유형
1. emptyDir
2. hostPath

#### EmptyDir
- 파드가 생성될 때 만들어지고, 파드가 삭제되면 함께 사라지는 임시 저장 공간
- 주로 캐시, 임시파일, 컨테이너간 파일 공유에 사용됨

#### hostPath
- Pod가 실행되는 노드의 특정 파일이나 디렉토리를 컨테이너에 직접 연결하는 볼륨
- 저장위치가 파드에 실행되는 노드의 파일시스템
- 주로 노드 로그, 시스템 파일, 런타임 소켓 접근에 사용됨

### 4.한계점
1. Volume은 영구 저장소가 아님
    - Node 또한 Auto-Scaling같이 삭제나 생성되기에 Node에 저장하는 것도 안전하지 않음.
2. 노드에 종속적임
3. 스토리지 운영을 직접 해야함.
    - Volume에는 보통 중요한 데이터를 저장하는데 사용하지 않음.
    - PV/PVC + StrageClass 여기에 중요한거 저장함.

## PV/PVC
- PV는 클러스터에 준비된 실제 저장공간
- PVC는 파드가 필요한 저장 공간을 요청하는 리소스
- Pod에서 저장공간이 필요함. -> PVC 저장공간을 요청함. -> 조건에 맞는 PV가 연결
- PV,PVC는 파드와 저장소를 직접적으로 연결하지 않음. 저장 공간을 제공하는 부분과 사용하는 부분을 분리해서 사용함.

### 1. PV
- Persistent Volume
- 클러스터에서 파드와 독립적으로 관리되는 저장공간
- 실제 저장소를 쿠버네티스 리소스로 추상화함.

#### 역할
1. 저장 공간 제공: Pod가 사용할 실제 저장소를 쿠버네티스 리소스로 표현
2. Pod와 수명 분리
3. **저장소 정보 캡슐화**: 저장소의 종류, 용량, 접근 방식 등을 PV에 정의해서 실제 저장소의 특성과 상관없이 일관적으로 사용 가능해짐.
4. 중앙 관리

### 2. PVC
- Persistent Volume Claim
- 조건을 적어서 해당 조건에 부합하는 저장공간이 필요하다고 요청함.
  - 필요한 용량
  - 읽기 쓰기 방식
  - 사용한 스토리지 종류
  
#### 역할
1. 저장 공간 요청
2. 저장소 추상화
3. PV와 연결
4. Pod가 PVC를 Volume으로 참조하여 사용

#### PVC YAML
```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-pvc

spec:
  accessModes:
    - ReadWriteOnce

  storageClassName: manual

  resources:
    requests:
      storage: 3Gi
```
- PVC가 요청한 것 중에서 항상 똑같이 해주지는 않음.
  - 만약 요청한 PV보다 큰 PV가 있으면 그냥 배정해줌.
  - 근데 요청한 PV보다 작은 PV가 있으면 배정하지 않음. (Pending 상태로 대기함.)
- 미리 만들지 않고 필요할 때 만들어서 주는 방식: StorageClass

#### PV, PVC의 바인딩 조건
1. 용량: 요청한 용량 이상이여야함.
2. 접근 모드: PVC가 요청한 접근 모드를 PV가 지원해야함.
3. StorageClass: 일치해야함
4. VolumeMode: 파일 시스템이나 블록 장치 모드가 호환되어야함.
5. Selector: PVC에 Selector이 있으면 PV 라벨이 조건을 만족해야함.
- 기본적으로는 일대일 관계인데 스토리지 시스템이 NFS, Access Mode에 따라서 접근하여 사용할 수 있음.

#### 접근 모드
| 접근 모드 | 약어 | 설명 |
| --- | --- | --- |
| ReadWriteOnce | RWO | 하나의 노드에서 읽기·쓰기로 마운트 |
| ReadOnlyMany | ROX | 여러 노드에서 읽기 전용으로 마운트 |
| ReadWriteMany | RWX | 여러 노드에서 읽기·쓰기로 마운트 |
| ReadWriteOncePod | RWOP | 하나의 Pod만 읽기·쓰기로 마운트 |
- 분산 스토리지인지 단일 스토리지인지 확인해야할 듯.

#### PV의 회수 정책
1. Retain: PVC가 삭제되어도, PV 안의 데이터를 자동으로 삭제하지 않음. (Released 상태로 그냥 대기함.)
2. Delete: PVC가 삭제되면 PV와 연결된 스토리지를 삭제할 수 있음.
    - 주로 Storage Class에 사용

#### 실무에서 사용 사례
- PV를 정적으로 만들어서 사용하는 것은 잘 안함. (스토리지를 낭비할 수 있어서 비효율적이기에)
- PVC를 만들었는데 PV가 없으면 StorageClass를 통해서 동적으로 PV를 생성하고 할당함.
- 데이터베이스로 사용
  - 강사님의 생각: 데이터베이스는 k8s로 관리하기는 적절하지 않은 것 같다.
- 상태 기반 애플리케이션
- 사용자 파일

#### 주의점
1. PVC 삭제 전, 회수 정책을 봐야함.
    - 회수 정책이 delete면 중요한 데이터가 삭제될 수 있음.
2. PV 영구적 저장소긴 하지만 자동으로 백업되지는 않음.
3. PV는 자동으로 줄어들지 않음.
4. PV는 정적으로 만든다면, 로컬 디스크 용량을 확인하는 것이 좋음.
5. 네임스페이스 구분
    - 내가 쓰려고 만든 PV를 다른 네임스페이스에서 가져갈 수 있음.
    - 그래서 라벨링으로 이러한 상황을 방지함.

## Storage Class
- PVC 요청에 따라서 어떤 종류의 저장소를 어떠한 정책으로 자동 생성할지 정의하는 스토리지 템플릿임.

### PV/PVC 한계
1. 관리자가 PV 생성하고 사용자가 PVC 생성함
2. Pod가 PVC 사용

### Storage Class로 해결
- 동적 프로비저닝으로 요청에 맞춰서 자동으로 PV를 만들어 사용함. (관리자가 PV를 미리 준비하지 않아도 됨.)


### 동작 구조
```
Pod
 │
 │ PVC 참조
 ▼
PersistentVolumeClaim
- storage: 10Gi
- storageClassName: fast
 │
 │ StorageClass 선택
 ▼
StorageClass: fast
- provisioner
- parameters
- reclaimPolicy
- volumeBindingMode
 │
 │ 실제 저장소 생성 요청
 ▼
Provisioner / CSI Driver
 │
 ├── 실제 Volume 생성
 └── PersistentVolume 생성
         │
         ▼
PVC와 PV 바인딩
         │
         ▼
Pod에서 Volume 사용
```

### Provisioner
- 프로비저너 PVC 요청을 보고 실제 저장소, PV를 생성하는 담당자
- 실제 저장소를 생성하는 기능은 프로비저너나 CSI Driver가 수행함.

### CSI
- Container Storage Interface
- CSI는 쿠버네티스와 외부 스트로지 시스템을 연결할 때 사용하는 인터페이스

#### 1. provisioner
- 어떤 스토리지 드라이버가 실제 볼륨을 생성할지 결정함.

#### 2. parameter
- 생성할 스토리지 세부 속성
- 이것은 실습이나 써봐야 알 수 있을 듯.

#### 3. reclaimPolicy
- reclaimPolicy: Retain
- PVC 삭제된 이후에 동적으로 생성된 PV랑 실제 저장소를 어떻게 처리하는지를 정의
    - Retain: 보통 사용함. 삭제해도 남김
    - Delete: 가능은 한데, 데이터가 정말 지워져도 괜찮은 경우에만 사용

#### 4. allowVolumeExpassion
- PVC 요청 용량을 증가할 수 있도록 허용할 것이지 여부 정의
- 조건
  - StorageClass에서 allowVolumeExpassion:ture
  - CSI Driver가 확장을 지원해야함
  - 실제 스토리지 시스템이 확장 지원해야함.
  - 파일 시스템이 확장 가능해야함.
- 축소는 대부분 지원을 안하기에 조심히 확장해야함.

#### 5. volumeBindingMode
- PV, PVC가 바인딩 될때, 실제 볼륨이 생성되는 시점을 결정
1. Immediate(Default): 즉시 Volume 생성 후 Pod 스케줄링.
2. WaitForFirstConsumer: Pod가 생성된 후에 적절한 위치에 Volume 생성
    - 가용영역을 컨트롤 하기에, 클라우드 환경에 유리함
    - 예시
      - Multi AZ일 경우, AZ-a,b가 있는데 a에 pod를 생성하고 b에 volume을 생성하는 비효율적인 상황이 발생함.
    - 대신 볼륨생성을 기다려야해서 지연시간이 발생함.
    - 또한 오토스케일링 같은 경우에 Pod를 추가해야하는데 Volume을 생성하지 못하는 경우 강제로 Pending되어서 확장이 안됨. (Volume 할당량을 초과한 경우 거절되는 경우가 있음.)

#### 서드파티 솔루션

1. OpenEBS
    - 쿠버네티스에서 로컬 디스크 + 분산 스토리지를 관리할 수 있도록 제공하는 클라우드 네이티브 스토리지 플랫폼
    - 온프레미스 환경이나 고성능 로컬 디스크를 사용하고 싶을때 사용함.

2. Ceph
    - 분산 스토리지를 Kubernetes Operator 방식으로 배포하고 관리하는 솔루션임.
    - 노드 간에 데이터 복제 (hostPath) -> 고가용성으로 구성할 수 있음. 대신 구성이 많이 복잡해짐.

## Controller
### StatefulSet
- 각 Pod의 고유한 이름, 네트워크 주소, 스토리지를 유지하면서 상태가 있는 애플리케이션을 관리하는 컨트롤러
- 동일한 파드를 만드는 것만 하는 것이 아니라 파드를 서로 구분하고 재생성되어도 기존의 이름과 스토리지를 다시 연결할 수 있도록 관리함.

#### 사용 이유
1. 파드 재생성시 이름 변경이 안됨
    - 데이터베이스 클러스터는 특정한 인스턴스가 특정 역할을 맡고 있어서 파드의 이름이 변경되지 않아야함.

2. 파드마다 다른 스토리지가 필요
    - 각 파드가 독립적인 스토리지를 유지해야할 때, `volumeClaimTemplates`: 각 파드에 고유한 PVC를 자동으로 만들어줌.
    - 파드가 삭제되어도 PVC가 남이 있어서, 같은 순번의 파드가 재생성 되면 기존 PVC를 사용해서 PV를 유지할 수 있음.
3. 특정 파드를 네트워크에서 찾아야함.
    - 일반적으로는 서비스를 사용하지만, 데이터베이스는 특정역할을 해야할 때가 있어서 좀 다름.

4. 파드의 생성과 삭제의 순서가 중요할 때가 있음.
- 분산 DB에서 master -> Replica  순서로 생성되어야함.

#### YAML
```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mysql
spec:
  serviceName: mysql-service
  replicas: 3

  selector:
    matchLabels:
      app: mysql

  template:
    metadata:
      labels:
        app: mysql
    spec:
      containers:
        - name: mysql
          image: mysql:8.4
          ports:
            - name: mysql
              containerPort: 3306

          env:
            - name: MYSQL_ROOT_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: mysql-secret
                  key: root-password

          volumeMounts:
            - name: data
              mountPath: /var/lib/mysql

  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes:
          - ReadWriteOnce
        storageClassName: standard
        resources:
          requests:
            storage: 10Gi
```

1. `serviceName`
- statefulSet Pod의 네트워크 도메인을 관리하는 서비스의 이름
2. `replicas`: 전에 배운 생성할 파드 수
3. selector, template
4. volumeClaimTemplates: 각 파드에 PVC를 자동으로 생성할 템플릿

#### 실무에서 사용하는 것
1. 데이터베이스 클러스터 구성
    - RDS MulitiAZ
      - 추가비용이 아주 많이 나옴
    - 그냥 k8s 사용하면 저렴하게 사용할 수 있음.
        - 하지만 설계가 복잡함.

2. 메시징
    - 메시지를 받아서 다른 쪽으로 전달해주는 메시지 브로커

#### 주의 사항
1. Liveness probe 를 과하게 설정하면 안됨.
    - 데이터베이스는 초기화 시간이 오래걸리고 커넥션 풀이 가득차면 요청을 처리하지 못함.
    - 그래서 짧게 설정하면 컨테이너는 영원히 재시작함.

2. StatefulSet이 데이터를 복제하지는 않음.
3. PVC, PV는 삭제하지 않아야함.
    - PV는 관리 주체가 클러스터라서 권한을 상다히 빡빡하게 줘야함.
4. 순차 생성은 연쇄 에러의 원인이 될 수 있음.
    - 내가 설정한 순서와 실제로 필요한 순서가 다르면 데드락 발생할 수 있음.

## Node Scheduling
- 새로 생성된 Pod를 실행할 수 있는 노드들을 찾고, 그 중 가장 적합한 노드를 선택하여 배치하는 과정
- 기본 스케줄러인 kube-scheduler는 두 단계를 거쳐서 파드가 실행될 노드를 결정함
    1. filtering - Pod를 실행 할 수 없는 노드를 제외
    2. Scoring - 실행 가능한 노드에서 가장 적합한 노드 선택
 
### 기본적인 스케줄링 동작
1. Filtering
- 노드 상태 확인
- 리소스 용량 확인
- 라벨링 확인
- Pod가 허용하지 못하는 Taint가 있는가 등등

2. Scoring
- 필터링을 통과한 후보 노드들의 점수를 매기는 과정

### 노드 스케줄링 제어 방식

| 방법 | 기준 | 강제성 | 특징 |
| --- | --- | --- | --- |
| 기본 스케줄링 | 리소스와 클러스터 상태 | 자동 | 일반적인 Pod 배치 |
| `nodeName` | 노드 이름 | 매우 강함 | 스케줄러를 우회하여 직접 지정 |
| `nodeSelector` | 노드 라벨 | 필수 | 단순한 `key=value` 조건 |
| Node Affinity `required` | 노드 라벨 조건식 | 필수 | 복잡한 필수 조건 |
| Node Affinity `preferred` | 노드 라벨 조건식 | 선호 | 가능하면 조건에 맞게 배치 |
| Taint/Toleration | 노드의 배치 거부 조건 | 허용 여부 | 특정 Pod만 노드에 들어오도록 제한 |

#### 1. nodeName: 이름을 명시해서 지정한 이름의 노드랑 연결하는 방식

#### 2. nodeSelector: 지정한 라벨을 모두 가진 노드에 파드를 배치하는 방식

#### 3. Node Affinity: 노드 라벨을 기반으로 필수 조건과 선호 조건을 세밀하게 표현하는 스케줄링 방식

- 두가지 조건식이 있음. 없으면 대기하던가 다른 노드에 가던가를 결정.
1. required~~
2. preferred~~

##### Node Affinity 연산자

| 연산자 | 설명 |
| --- | --- |
| `In` | 노드 라벨 값이 지정된 목록에 포함되어야 함 |
| `NotIn` | 노드 라벨 값이 지정된 목록에 포함되지 않아야 함 |
| `Exists` | 해당 라벨 키가 존재해야 함 |
| `DoesNotExist` | 해당 라벨 키가 없어야 함 |
| `Gt` | 라벨 값이 지정한 숫자보다 커야 함 |
| `Lt` | 라벨 값이 지정한 숫자보다 작아야 함 |

  ##### AND , OR
- and
    ```yaml
    nodeSelectorTerms:
    - matchExpressions:
        - key: env
            operator: In
            values:
            - production
        - key: disktype
            operator: In
            values:
            - ssd
    ```

- or
    ```yaml
    nodeSelectorTerms:
    - matchExpressions:
        - key: env
            operator: In
            values:
            - production

    - matchExpressions:
        - key: disktype
            operator: In
            values:
            - ssd
    ```

#### 4. Taint , Toleration
- Taint는 노드가 Pod를 밀어내는 제한 조건
- Toleration은 Pod가 그 제한을 견딜 수 있는 조건
  - Toleration으로 Taint를 무사해서 filtering 단계는 통과하지만 Scoring에서 걸러질 수 있음.
