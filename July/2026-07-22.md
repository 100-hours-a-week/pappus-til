### Job
- Job은 한 번 실행하고 정상적으로 끝나야하는 작업을 관리하는 컨트롤러임.
- deployment는 애플리케이션을 계속 실행상태로 유지

#### 사용 이유
- 일반 파드로 실행하면 작업 실패했을 때 다시 실행해야하는데, 작업이 실패한 파드 로그를 보고있어야함.
- 예시) 데이터베이스 마이그레이션
  - mysql에서 mongo DB로 변경하려함. (400GB)
  - 파드 하나로 작업하기에는 시간이 너무 오래걸림.
    - 중간에 실패하면, 어디까지 성공했는지 어디부터 다시 시작하면 되는지를 신경써야해서 번거로움.
  - 처리를 하고 있는데, 처리 속도보다 신규 데이터 작성 속도가 빠르면, 영원한 작업이 됨.
  - 이럴때는 파드 여러개를 띄워서 병렬로 처리함.
    - 이러면 
- Job은 작업이 성공할때까지 해당 작업에 사용되는 파드를 관리함.

```
try-catch 주의 사항
catch로 넘기면 exit 0으로 되서 job이 실패했다는 것을 감지하지 못해서 성공으로 처리함
```

#### 핵심 설정
1. Completions: 전체 작업이 완료되기 위해 필요한 성공 횟수
2. parallelism: 동시에 실행할 수 있는 파드 수
3. restartPolicy: 재시도 할지 말지 정하는 정책
    - OnFailure: 실패하면 재시도
      - backoffLimit: 몇 번 재시도 할건데?
    - Never:실패하면 중지

#### 실무에서 사용하는 예시
1. 데이터베이스 초기화
2. 데이터베이스 스키마 마이그레이션
3. 일회성 데이터 변환 등등

### CronJob
- 정해진 시간마다 Job을 생성하는 컨트롤러
- concurrencyPolicy: 이전 Job이 끝나지 않았는데, 다음 실행 시간이 됐을때 처리 방식
    1. Allow: 그냥 실행
    2. Forbid: 건너뜀
    3. Replace: 이전 Job 종료 후 실행

    ```

    4. 노드에 패킷 전달 규칙을 구성한다.
    --- 여기까지

    5. Service 트래픽이 들어오면 **커널이** 규칙에 따라 Backend를 선택한다.

    6. 패킷의 목적지를 Service IP에서 Pod IP로 변경한다.
    ```

- 동작 모드
  - `iptables`
  - IPVS
  - nftables

#### 네트워크 구성 요소

### CNI
- Pod가 생성되거나 삭제될 때 네트워크 인터페이스, IP 주소, 라우팅 등을 설정하고 정리하기 위한 표준 규격

#### 사용 이유
1. 네트워크 설정 자동화
2. 표준화: 컨테이너 런타임이 특정 네트워크 제품의 구현 방법을 알 필요 없음.
3. 플러그인 선택 가능
4. Pod IP 관리: 중복되지 않는 IP를 할당하고 회수할 수 있음.
5. 노드 간 통신 구성: 서로 다른 노드에 있는 Pod 통신이 가능하도록 경로를 구성함.
6. 환경 확장
  
#### CNI 플러그인 종류
1. Flannel
    - 단순한 구조, 파드간 네트워크 연결에 집중하는 CNI 플러그인
    - NetworkPolicy 기능은 제공하지 않음.
2. Calico
    - 네트워크 구성 방식 다양하게 지원
      - BGP
      - IP in IP
      - VXLAN
  - 실무적으로는 칼리코 적용이 일반적
  - BGP사용하는 네이티브 라우팅
  - 오버레이 네트워크 (IP in IP, VXLAN)
3. Cilium
    - eBPF

#### CNI , kube-proxy 차이
| 구분 | CNI 플러그인 | kube-proxy |
| --- | --- | --- |
| 주요 대상 | Pod 네트워크 | Service 네트워크 |
| 주요 역할 | Pod에 IP를 부여하고 통신 경로 구성 | Service IP로 온 요청을 실제 Pod Endpoint로 전달 |
| 동작 시점 | 주로 Pod 생성·삭제 시 네트워크 설정 | Service와 EndpointSlice 변경을 감지해 전달 규칙 구성 |
| 예시 | Flannel, Calico, Cilium | iptables, IPVS, nftables 등의 구현 모드 |
- 이렇게 나와있는데 개인적인 생각으로는 구현은 CNI 플러그인, 구현된 것이 잘 동작하도록 운용하는 것은 kube-proxy와 Service라고 생각함. 

### VXLAN, IP in IP, BGP
#### VXLAN
- 이전에 배웠지만 다시 한번 기억하지면, TCP를 UDP에 담아서 서로 다른 Node에 있는 Pod끼리 통신하기 위한 방법

#### IP in IP
- IP레이어에서 새로운 IP로 담음.
- 동작은 VXLAN과 비슷함. 둘다 캡슐화를 함.

| 구분 | VXLAN | IP-in-IP |
| --- | --- | --- |
| 캡슐화 대상 | 이더넷 프레임 | IP 패킷 |
| 계층 관점 | Layer 2 over Layer 3 | Layer 3 over Layer 3 |
| 외부 프로토콜 | UDP | IP Protocol 4 |
| 주요 헤더 | Outer IP + UDP + VXLAN | Outer IP |
| 오버헤드 | 더 큼 | 상대적으로 작음 |
| 네트워크 호환성 | UDP이므로 비교적 통과가 쉬운 편 | IP Protocol 4 허용 여부 확인 필요 |
- 의문: 그냥 보면 ip in ip가 오버헤드가 작아서 상위호환처럼 보임. 하지만 이렇게 기술이 분리되어서 존재하는 것인 이유가 있을텐데 뭐지?
- **고민한 결과 **
  - Cisco에서 소개하길 VXLAN으로는 L2를 IP 네트워크의 어느 곳으로나 확장할 수 있다고 설정이 나옴. 한마디로 L2에 있는 데이터를 안전하게 L3 환경에서도 전달 할 수 있도록 하여 L2 영역을 확장하는 기술인데 k8s에서 사용하는 것임. 
  - 이것을 다른 Node간의 Pod와 통신하기 위해서 사용하니까 오버헤드가 발생하는 것임. Pod는 IP가 있어서 Ip in IP로 충분한데, 전달 할 수 있다는 것 이유 하나로 VXLAN을 사용하는 것은 비효율적임.
  - 출처: [Cisco VXLAN](https://www.cisco.com/c/ko_kr/support/docs/switches/nexus-9000-series-switches/118978-config-vxlan-00.html)


#### BGP
- 어떤 IP 대역에 도달하려면 어느 이웃에 보내야하는지 네트워크 장비 사이에서 교환하는 라우팅 프로토콜
- 주변에 자신이 가지고 있는 라우팅 테이블을 광고하는데 prefix만 광고함.
- 개인적인 생각: 왜 BGP만 사용하지? RIP,OSPF는?
  - 이유: BGP와 같은 라우팅 프로토콜인 RIP, OSPF도 사용 가능하지만 k8s는 보통 서비스의 규모가 커졌을 때 사용하므로 RIP,OSPF와 같은 것보다 BGP가 더욱 적합하여 BGP를 사용함.

##### 작동 순서
1. BGP 이웃 관계 형성
2. 서로 라우팅 테이블을 광고
3. 수신한 경로를 라우팅 테이블에 반영
4. 실제 파드 패킷 전달

##### BGP 방식
1. Full Mesh: 모든 노드가 서로 BGP를 맻게됨
2. BGP Reflector: Route Reflector를 만들어서 거기에 경로를 저장하는 방식

##### BGP 패킷 전달 방식
1. Native Routing
   - 물리적인 하드웨어를 다룰 수 있을 때 좋음.
2. IP in IP랑 같이 사용
    ```
    1. BGP가 경로를 알려줌
    10.244.2.0/24 → Node B

    1. Node A가 그 경로를 선택함

    2. IP-in-IP로 패킷을 캡슐화함
    Outer: Node A → Node B
    Inner: Pod A → Pod B

    1. Node B에서 디캡슐화함
    ```
#### VXLAN 예시

```
Pod A
  ↓ 원본 Ethernet Frame
Node A VTEP
  ↓ UDP + VXLAN으로 캡슐화
Underlay Network
  ↓ Node IP 기반 전달
Node B VTEP
  ↓ 디캡슐화
Pod B
```

#### IP-in-IP 예시

```
Pod A
  ↓ 원본 IP Packet
Node A
  ↓ Outer IP Header 추가
Underlay Network
  ↓ Node IP 기반 전달
Node B
  ↓ Outer IP Header 제거
Pod B
```

#### BGP 직접 라우팅 예시

```
Pod A
  ↓ 원본 IP Packet
Node A
  ↓ BGP로 학습한 경로 조회
Underlay Network
  ↓ Pod IP 패킷 그대로 전달
Node B
  ↓ 로컬 Pod 경로 조회
Pod B
```

#### 언제 어떤 것을 선택하면 좋을까?
##### VXLAN가 적합할 때

- 언데레이 네트워크 (물리 네트워크) 를 수정하기 어려울 때
- 클라우드 환경에 적합함
- UDP 트래픽을 사용하기 좋은 환경
    - 열어서 사용해도 괜찮을 때
    - 구현이 단순해도 괜찮을 때
    - 호환성이 좋을 때
- 단점
    - 캡슐화 헤더가 크고
    - MTU 를 조정해야함

##### IP in IP 가 적합할 때

- Layer 3 ← 전송
    - 단순한 캡슐화
- 언데레이 네트워크가 IP 프로토콜 L4 을 허용할 때
- VXLAN 보단 캡슐화를 작게하고 싶을 때

##### BGP가 적합할 때

- 언더레이 네트워크 장비들에 Pod CIDR 경로를 설치할 수 있을 때
    - BGP 네이티브 말고
    - IP in IP 방식 사용할 수 있는데..
        - 장비에 따라서 허용하지 않는 장비가 있음.
- 캡슐화 오버헤드를 줄이고, 속도를 가져가겠다.
- 대규모 환경에서 사용한다.
- 네트워크 팀이 직접 BGP 을 운영할 수 있을 때
- 단점
    - 네트워크 구성과 운영 난이도가 상당히 높아진다..
