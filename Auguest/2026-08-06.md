## 캐시 문제 해결
- 데이터베이스의 부하를 줄이기 위한 장치지만 잘못 설계하면 트래픽을 데이터베이스로 한꺼번에 전달하는 장애 증폭기가 될 수 있음.

1. 캐시
    - 자주 조회하거나 리소스 비용이 큰 데이터를 빠르게 서빙하기 위해서 임시 저장소에 보관하는 방식
    - 데이터베이스나 외부 API의 접근을 줄이는 방식임.

### 일반적인 사용 방식
1. Cache Aside Pattern
    - 캐시를 먼저 조회하고 캐시에 없으면 DB를 본 후에 데이터가 있으면 캐시에 데이터를 저장하고 사용자에게 데이터를 반환함.

### 캐시의 문제
1. 존재하지 않는 데이터가 반복 조회함. Cache Penetration
2. 인기있는 하나의 캐시가 완료됨. Cache Stampede / Cache Breakdown
3. 많은 캐시가 한꺼번에 사라짐. Cache Avalanche
4. 특정 키에 요청이 집중됨. Hot Key
5. 캐시와 데이터베이스의 값이 달라짐. Cache Consistency

#### 1. Cache Penetration
- 존재하지 않는 데이터가 반복적으로 조회됨.
- 공격자가 없는 상품을 계속 조회해서 DB를 타격하는 방법으로 공격함.
  
1. 입력값을 검증
2. 존재하지 않는 결과를 캐싱
    - 이러한 캐싱은 메모리를 차지하기에 TTL을 작게 설정하는 것이 좋음.
3. 블룸 필터
    - 특정 데이터가 존재하지 않는다는 것을 확률적으로 계산해서 리턴하는 방식
    - 자료 구조상 존재하지 않을 것 같다라는 것으로 거르는 필터
    - 데이터 양이 많으면 블룸 필터가 잘 작동하지는 않음.

##### Boolm Filter
- 찾는 요소가 집합의 구성원인지 아닌지의 여불르 확인하는데 공간 효율적인 확률적 데이터 구조
- 집합에 없더라도 있다고는 나타낼 수 있지만, 없는 것일 있다고 하지는 않음. 그래서 필터링할 때 해당 특성을 활용하면 좋은 필터링을 할 수 있을 듯 함.
- 원리는 고정 크기 비트 배열의 여러 비트를 매핑해서 일치한다면 있다고 판단하고 없으면 없다고 판단하는 방식임
  - 이러한 원리로 많은 데이터가 있으면 대부분 1로 가득하기에 대부분 있다고 거짓으로 판단할 경우가 많아져서 효율이 상당히 떨어질 수 있음.

1. Rate Limit
    - 조회 횟수를 제한해서 공격을 막음.
    - 하지만 분산 되어 있는 공격자를 막을 수는 없음.

#### 2. Cache Stamped
    - 인기 있는 캐시 하나가 만료되는 순간, 많은 요청이 동시에 데이터베이스를 조회하는 문제

1. Request Coalescing
    - 동일한 키에 대한 요청을 was에서 홀딩하고 같은 요청이면 하나로 합쳐서 DB에서 조회한 후 결과로 응답함.
2. 키 단위 락 걸기
    - 캐시에 없을 때, 가장 먼저 도착한 요청만 락을 획득해서 DB를 조회하는 방식
    - 하지만 락 자체가 병목이 될 수도 있음.
      - 락에다가 TTL을 걸어서 제거할 수 있음
      - 락 획득 실패시 캐시에 
3. Stale-While-Revalidate
    - 캐시가 논리적으로 만료되어도, 기존데이터를 잠깐 반환시키고 백그라운드에서 캐시를 갱신
4. 만료 전에 미리 갱신
    - 스캐줄러를 통해서 캐싱을 미리 갱신하는 방식 (CronJob)
    - 인기 키만 골라서 갱신하지 않으면, 쓸모없는 것들까지 갱신하게 됨.

#### 3. Cache Avalanche
- 많은 캐시 키가 동시에 만료되거나 캐시 서버 전체에 장애가 발생해서, 대량의 요청이 한꺼번에 DB에 들어오는 문제

**원인**
1. 신규 파드, 신규 서비스를 시작할 때
    - 서비스 시작할 때, 여러 데이터를 한 번에 캐싱하게 되는데, 이후 TTL이 같아서 모든 키가 만료되면 캐시 미스가 동시에 일어나서 DB에 부하가 몰리게 됨.
2. 캐시 서버 장애
3. Cold Cache
    - 레디스 재시작, 신규 서버나 리전 오픈 등

**해결 방식**
1. Jitter 적용
    - 모든 캐시에 TTL을 동일하게 설정해서 발생하는 문제이기에, TTL을 랜덤하게 하도록 해서 만료 시간을 분산시킴.
    - 캐시 자체가 많아지면 TTL 분산을 해도 용량이 커지면 똑같은 현상이 발생함.
2. Cache Warm-Up
    - 캐시 서버를 새롭게 만들 때, 미리 데이터를 넣어두고 준비가 되었을 때 서비스 시작.
3. 캐시서버 장애가 문제면 고가용성으로 만들어서 방지
