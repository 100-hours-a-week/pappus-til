# 주제 1: 객체지향 프로그래밍(OOP)

# OOP(Object Oriented Programming)란?

객체지향 프로그래밍은: 프로그램을 "일의 순서" 중심이 아니라
"객체들의 협력" 중심으로 설계하는 방식

---

# 객체란?

객체는 : 자신의 역할이 있고, 그 역할을 책임지는 주체

- 역할(Role)
- 책임(Responsibility)

---

# 자동차 예시

## 엔진 객체

```text
"나는 시동을 걸고,
바퀴에 회전을 전달하는 역할을 책임진다."
```

---

## 중요한 점

엔진의 역할이 "회전을 전달하는 것" 이라면,
그 내부 구현이 휘발유 , 전기 , 수소 중 무엇을 사용하든 상관없다.

---


# 개인적인 의문

## "최소 기능"의 기준은 무엇인가?

객체지향은 작은 기능들을 조립하여 큰 객체를 만든다.

```text
"어디까지 쪼개야 최소 기능인가?"
```

개인적으론 최소 기능의 기준은 "하나의 책임을 설명할 수 있는가?" 인 것 같다.

객체는 하나의 역할 이나 하나의 책임을 가지도록 설계하는 것이 중요하다.

---

# 주제 2: SOLID 원칙

# SOLID란?

- 객체지향 설계를 더 유지보수 가능하고 확장 가능하게 만들기 위한 핵심 원칙들이다.
- 유지보수성 + 확장성 증가

# SOLID 구성

# S - SRP (Single Responsibility Principle)

- 단일 책임 원칙
- 클래스를 수정해야 하는 이유는 하나여야 한다.

책임이 많아질수록:
- 수정 범위 증가
- 사이드 이펙트 증가
- 유지보수 어려움

---

# 예시

## 잘못된 경우

```text
UserService
- 회원가입
- 로그인
- 이메일 전송
- 파일 저장
```

→ 책임 과다

---

# 좋은 경우

```text
UserService → 회원 처리
MailService → 메일 처리
FileService → 파일 처리
```

→ 역할 분리

---

# 개인적인 생각

```text
수정 범위를 최소화하는 것이 핵심인 것 같다.
```

---

# O - OCP (Open Closed Principle)

- 개방-폐쇄 원칙
- 확장에는 열려 있고, 수정에는 닫혀 있어야 한다.
- 새 기능 추가할 때 기존 코드 수정 최소화

---

# 개인적인 생각

```text
기능 추가할 때
기존의 다른 코드는 건드리지 마라.
오래된 스위치에 먼지가 있으면
그것마저 부품이다.
```

이미 잘 동작하는 기존 코드는 함부로 수정하지 않는 것이 중요하다.

---

# 예시

## 나쁜 예시

```java
if(type.equals("car")) {
}

else if(type.equals("bike")) {
}
```

기능 추가마다:
- 기존 코드 수정 필요

---

# 좋은 예시

```text
인터페이스 추가
→ 구현체 추가
```

만 하면 된다.

---

# L - LSP (Liskov Substitution Principle)

- 리스코프 치환 원칙
- 자식 클래스는 부모 클래스를 대체할 수 있어야 한다.
- 부모 타입을 사용하는 곳에서 자식 객체가 들어가도 정상 동작해야 한다.

# I - ISP (Interface Segregation Principle)

- 인터페이스 분리 원칙
- 거대한 인터페이스 하나보다 작게 분리된 인터페이스를 사용하자.
- 필요하지 않은 기능까지 구현하게 만들지 말자.

# D - DIP (Dependency Inversion Principle)

- 의존관계 역전 원칙
- 구체적인 것보다 추상적인 것에 의존하라.
- 구현체가 아니라 인터페이스에 의존

# 왜 중요할까?

구현체 교체가 쉬워짐.
- 유지보수
- 테스트
- 확장성

---

# SOLID 핵심 정리

| 원칙 | 핵심                |
|-----|---------------------|
| SRP | 책임 하나            |
| OCP | 확장 가능 / 수정 최소 |
| LSP | 자식은 부모 대체 가능  |
| ISP | 인터페이스 분리       |
| DIP | 추상화 의존          |

# Byte Code File 내부

a) Constant Pool
- 바이트 코드 내부의 테이블
- 실행 중 필요한 이름들을 인덱스로 관리하는 테이블

저장 내용

- 클래스 이름
- 메서드 이름
- 문자열
- 참조 정보 등 메타데이터 저장.

---

b) Default Constructor

- 컴파일러가 자동 생성하는 기본 생성자

---

# JVM 실행 흐름

# 1. Class Loader
- 바이트 파일을 JVM 메모리에 로딩

## 특징

Java는:
- 프로그램 시작 시, 모든 클래스 로딩 X
- 필요한 클래스만 로딩

---

## Class Loader 과정

### 1) Loading
- .class 파일을 Method Area에 올림

### 2) Linking
- 클래스를 실행 가능하게 검증하는 과정

a) Verifying: JVM 명세에 맞는지 검증
b) Preparing: 메모리 할당
c) Resolving : 심볼릭 레퍼런스 -> 실제 메모리 참조로 변경

### 3) Initialization
- 클래스 변수 초기화

---

# 2. Execution Engine
- 바이트 코드를 기계어로 변환함.

## 1) Method Area
- 클래스 정보 저장 영역.
- 클래스 정보, 메서드 정보, static 변수, 런타임 상수 풀 등 저장

## 2) Interpreter
- 한 줄씩 해석하며 실행.
- 문제 : 반복 실행 시 느림.

## 3) JIT Compiler
- 자주 사용하는 코드를 기계어로 컴파일하여 캐싱한다.
- 자주 쓰는 함수는 미리 캐싱

## 4) Garbage Collector
- 사용하지 않는 메모리 회수.
- Heap 영역 정리

---

# 3. Runtime Data Area

## JVM 메모리 영역
- Method Area + Heap + Thread

## 1) Method Area
- 클래스 메타정보 저장.

## 2) Heap
- 참조 객체 저장.
- new로 생성한 객체 저장

## 3) Thread 구조

Thread = PC Register + JVM Stack + Native Method Stack

### a) JVM Stack
- LIFO
- Stack Frame : 메서드 실행 시 필요한 정보 저장. (지역 변수, 매개 변수, 참조 변수)

### b) PC Register
- 현재 실행 위치 기록
- 스레드마다 존재

### c) Native Method Stack

- C , C++ 같은 Java 외부 코드 실행용 Stack
- 근데 이건 왜 있는거지? => 자바 내에서 외부함수를 호출하는데 그것인 java가 아닌 다른 언어로된 함수인 경우가 있어서.

# JVM 전체 흐름 정리

```text
.java
↓
javac
↓
.class(Byte Code)
↓
Class Loader
↓
Runtime Data Area 적재
↓
Execution Engine 실행
↓
JIT 캐싱
↓
GC 메모리 정리
```

# 오늘의 회고

오늘은 객체지향 프로그래밍과 JVM 구조를 학습하였다. 이전까지 객체지향에 대해서 충분히 배웠고 이해했다고 생각했는데 학습하면서 예시를 보면서 생각보다 객체지향을 지키기 위해서는 기능을 새분화 해야하고, 객체지향의 핵심은 결국 객체들의 역할과 책임을 어떻게 나누고 협력하게 만들 것인가에 있다는 점이 인상 깊었다.

또한 객체를 무작정 잘게 나누는 것이 아니라 “하나의 책임을 자연스럽게 설명할 수 있는가?”를 기준으로 설계해야 한다는 점도 고민하게 되었다. 아직 어디까지를 최소 기능으로 봐야 하는지는 완전히 정리되지는 않았지만, 이것은 경험을 쌓으면서 느낄 수 밖에 없다고 생각한다.

JVM 구조도 단순 암기보다는 실제 실행 흐름으로 연결해서 이해하려고 하니 훨씬 흥미롭게 느껴졌다. Java 코드가 바로 실행되는 것이 아니라 `.java` 파일이 컴파일되어 `.class` 바이트 코드가 되고, Class Loader가 필요한 클래스만 메모리에 올린 뒤 Execution Engine이 이를 실행한다는 흐름이 이전보다 훨씬 구조적으로 이해되었다. 특히 Interpreter와 JIT Compiler의 차이, 자주 사용하는 코드를 캐싱하여 성능을 높인다는 점이 인상 깊었다.

오늘 배운 것은 크개 SOLID 규칙과 JVM 구조인데 특히 JVM 구조를 공부할 때가 힘들지만 재밌던것 같다. 
다시 정리하면서 JVM이 왜 Native Method Stack같은게 있는지 생각하고 JIT Compiler로 캐싱을 통해 최적화 하려는 것도 신기했다.
