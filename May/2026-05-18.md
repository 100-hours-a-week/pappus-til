# 새로 배운 내용

## 주제 1: 웹(Web)의 발전 과정과 특징

### 웹 1.0
- 시기 : 1990년대 초반
- 특징 : 읽기 전용 웹
- 사용자는 단순히 정보를 소비하는 역할
- 기업이나 기관이 만든 정보를 사용자가 읽는 형태

예시
- 기업 소개 페이지
- 단순 게시판
- 뉴스 사이트

### 웹 2.0
- 시기 : 2000년대 초반
- 특징 : 사용자 참여 중심
- 양방향 소통 가능
- 사용자가 직접 정보를 생산하고 공유

예시
- 유튜브
- 블로그
- SNS
- 위키피디아

느낀점
- 웹 1.0은 "정보 제공" 중심이었다면
- 웹 2.0은 "참여와 공유" 중심이라는 차이

### 웹 3.0
- 아직 완전히 정착하지 않은 단계
- 핵심 키워드
    - 개인화
    - 탈중앙화
    - 지능화

#### 개인화
- AI와 머신러닝 기반 추천 시스템
- 사용자 맞춤형 서비스 제공

#### 탈중앙화
- 데이터를 중앙 서버 하나가 아닌 여러 컴퓨터에 분산 저장
- 블록체인 기술과 관련이 깊음

#### 보안성 증가
- 데이터가 하나의 서버에 집중되지 않기 때문에 보안성이 증가
- 개인이 자신의 데이터를 직접 관리하려는 흐름이 강해짐

추가적으로 인상 깊었던 내용
- 최근 AI 시대에서 데이터 소유권 문제가 중요해지고 있음
- 사용자가 생성한 데이터를 빅테크 기업에게 주지 않으려는 흐름 존재
- 그래서 AI 모델도 로컬 환경에서 실행되도록 경량화되는 추세

# 주제 2: 클라이언트 - 서버 구조

## 클라이언트(Client)
- 서비스를 요청하는 주체
- 보통 네트워크 통신을 먼저 시작함
- 사용자 인터페이스를 제공함

예시
- 웹 브라우저
- 모바일 앱
- 게임 클라이언트

브라우저 역할
- HTML, CSS, JavaScript 데이터를 받아 사용자에게 화면으로 보여줌

## 서버(Server)
- 서비스를 제공하는 주체
- 특정 포트를 열어두고 요청을 기다림
- 요청이 들어오면 응답함

서버 특징
- 비즈니스 로직 처리
- 데이터 저장 및 관리
- 접근 제어와 보안 담당

---

## 서버 종류

### Web Server
정적 자원을 처리하는 서버

예시
- Nginx
- Apache

정적 자원 예시
- HTML
- 이미지
- CSS

### WAS(Web Application Server)
동적인 처리를 담당

예시
- Tomcat
- Jetty

역할
- Java 코드 실행
- 비즈니스 로직 처리

### Database Server
데이터를 저장하고 관리

예시
- MySQL
- MariaDB

---

## 왜 클라이언트와 서버를 분리했을까?

### 과거 구조
1970~80년대에는 중앙 컴퓨터가 대부분의 연산을 처리

구성
- 메인프레임
- 더미 터미널

문제점
1. 비용이 매우 비쌈
2. 중앙 집중 처리로 병목 현상 발생
3. 확장성이 낮음

### 변화
개인용 컴퓨터 보급 이후
- 일부 연산을 개인 컴퓨터가 처리하기 시작

효과
1. 비용 절감
2. 사용자 경험 증가
3. 유지보수 향상
4. 확장성 증가

---

# 주제 3: HTTP

## HTTP(HyperText Transfer Protocol)
웹에서 데이터를 주고받기 위한 통신 규약

내 생각
- 결국 HTTP는 "웹에서 어떻게 대화할지에 대한 약속" 같다. (문법같은 느낌?)

---

## HTTP 특징

### Request / Response 구조
클라이언트가 요청(Request)을 보내고 서버가 응답(Response)을 반환

---

## HTTP Message 구조

### 1. Start Line
- 요청 방식
- URL
- 프로토콜 버전 정보 포함

### 2. Header
- 데이터에 대한 설명
- 메타데이터 역할

예시
- Content-Type
- Authorization

### 3. Empty Line
- Header와 Body 구분

### 4. Body(Payload)
- 실제 데이터

---

# HTTP Method

GET / 데이터 조회
POST / 데이터 생성
PUT / 데이터 전체 수정
PATCH / 데이터 일부 수정
DELETE / 데이터 삭제

---

## HTTP Method를 나눈 이유

### 1. 서버 부하 감소
- 요청 내용을 열어보지 않아도 어떤 행동인지 파악 가능

### 2. 캐싱 효율 증가
- 조회 요청을 캐싱하기 쉬움

### 3. 보안
- 수정/삭제 같은 위험한 요청을 쉽게 구분 가능

내 생각
- Method는 결국 요청의 목적을 빠르게 파악하기 위한 라벨 역할 같다.

---

# HTTP Status Code

1xx / 정보 전달
2xx / 성공
3xx / 리다이렉션
4xx / 클라이언트 오류
5xx / 서버 오류

흥미로웠던 부분
- 서버는 보안을 위해 자세한 오류 정보를 숨기기도 함
- 그래서 실제 서비스에서는 500으로 묶어서 처리하는 경우도 많음

---

# HTTP URL

## 구성 요소

### 1. 스키마(Scheme)
- 사용할 프로토콜

예시
- http
- https

### 2. Domain / Port
- 요청 대상 서버
- 포트는 서버 내부 게이트 역할

### 3. Resource Path
- 리소스 위치

### 4. Query Parameter
- 추가 조건 전달

---

# Query String & Path Variable

## Query String
추가적인 조건 전달

사용 예시
- 정렬
- 필터링
- 검색 옵션

예시
/users?gender=male

---

## Path Variable
리소스를 식별하기 위한 값

예시
/users/1

---

## 둘의 차이

### Query String
- 필수 조건이 아님
- 부가적인 옵션

### Path Variable
- 리소스를 식별하는 핵심 정보

내가 이해한 방식
- 특정 사람을 찾는다면 Path Variable
- 남자만 찾는다면 Query String

---

# REST API

## REST란?
웹의 특징을 잘 활용하기 위한 아키텍처 스타일

핵심
1. 리소스
2. 메서드
3. 메시지

---

## RESTful한 URL 고민

### 회원가입 API

내 생각
POST /users/signup

강사님 의견
POST /users

느낀점
- REST는 URL에 행동을 넣기보다 리소스를 표현하는 것을 중요하게 생각한다.
- 행동은 Method로 표현한다는 개념이 인상 깊었다.

---

## Soft Delete

유저 삭제 시
- 실제 삭제가 아닌 상태만 변경

이유
- 일정 기간 복구 가능하게 하기 위해

흥미로웠던 부분
- 내부 구현은 PATCH 느낌이지만
- 외부 사용자 입장에서는 DELETE가 더 자연스럽다는 점

# 주제 4: Spring Framework

## Spring 등장 배경

### JSP 문제점
- HTML과 Java 코드가 섞임
- 유지보수 어려움

### EJB 문제점
- 설정 복잡
- 무거움
- 테스트 어려움

결과
- 코드가 커질수록 객체 관리가 어려워짐
- new를 남발하게 됨
- 결합도가 증가

---

# Spring 핵심 개념

## IoC(Inversion of Control)

### 제어 역전
객체 생성과 생명주기를 컨테이너가 관리

기존 방식
```java
MemberService service = new MemberService();
```

Spring 방식
- 컨테이너가 객체 생성 및 주입

느낀점
- 객체 관리 책임을 프레임워크에게 넘긴다는 개념이 핵심인 것 같다.

---

## DI(Dependency Injection)

필요한 객체를 외부에서 주입받는 방식

### 종류
1. 생성자 주입
2. 필드 주입
3. 세터 주입

생성자 주입이 좋은 이유
- 객체 불변성 유지
- 테스트 용이

---

## AOP(Aspect Oriented Programming)

공통 관심사를 분리하기 위한 기술

예시
- 로그
- 인증
- 트랜잭션

장점
- 중복 코드 감소
- 유지보수 향상

---

# 한 줄 정리

 - Web : 사용자들이 정보를 주고 받는 가상 속 광장같은 곳
 - 클라이언트 : 서버에게 데이터를 요청하는 것
 - 서버 : 클라이언트에게 데이터를 주는 것
 - HTTP : 네트워크 통신을 원활히 하기 위한 약속
 - HTTP Mesasge : 데이터를 담는 곳
 - HTTP Method :  데이터를 어떻게 하면 좋을지 라벨링 하는 곳
 - HTTP Status Code : 응답 결과를 코드화 해서 약속한 것 
 - HTTP URL : 리소스에 접근하기 위한 주소
 - Query String : 필수적이지 않는 추가적인 조건을 적는 곳
 - Path Variable : 필수적인 조건을 적는 곳
 ex) 사람을 찾을 때 특정한 사람을 찾으려면 이름을 path variable에 넣어야함 하지만 남자를 찾고 싶다하면 Query String으로 넣음.
======================================한 줄 정리 / 사용 이유============================================
 - RESTful API : HTTP규칙을 잘 활용하기 위한 규칙 / 통신을 원활하게 하기 위해서
 - 스프링 : 자바를 활용해 대규모 개발을 가는하게 하는 도구 / 코드의 규모가 커질 수록 어떤 객체가 있는지 알기 어려워서 계속 생성하여 사용하게 되어 java특성을 잘 활용하지 못하게 되어서.
 - IoC : 객체관리에 대한 부담을 덜어주는 것 / 코드가 많아지면 어떠한 객체를 생성했는지 알기 어려워져서 관리가 힘들어져서.
 - DI : 객체관리하기 위해 컨테이너에 등록하는 것 / 코드가 많아지면 어떠한 객체를 생성했는지 알기 어려워져서 관리가 힘들어져서.
 - AOP : 공통적 기능을 편하게 적용시키기 위해서 / 공통적인 기능을 적용하려면 복사 붙혀넣기로 하나하나 집어넣어서 적용해야하는 것이 번거로워서
 - Spring bean : Spring container가 관리하기위한 객체의 기본적인 단위 / 코드가 커져도 객체를 재사용할 수 있게 하기 위해서
 - 빈 컨테이너 : bean을 관리하는 관리소 / 코드가 커져도 객체를 효율적이고 적절하게 사용할 수 있도록 하기 위해서

아직 완벽하게 이해하지 못한 부분도 많다.
특히 IoC와 DI는 직접 코드로 실습해보면서 더 익숙해져야 할 것 같다.
