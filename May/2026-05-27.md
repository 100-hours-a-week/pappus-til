## HTTP 자격 증명 헤더

- 클라이언트와 서버 간의 인증과정에서 사용자의 자격을 확인하기 위해 사용되는 헤더

#### WWW-Authenticate
- 서버가 발급하는 Response Header
- 이 요청은 인증이 필요해
- 401 (Unauthroized) 

### Authorization
- 클라이언트가 요청할 때 보내는 헤더
- 신분을 증명하는 내용을 이 헤더에 담음.

### HTTP 인증 헤더 방식 3가지
### 1. Basic Authentication

- 기본인증인 아이디 + 패스워드
- 아이디:패스워드 -> Base64 인코딩 

```
Authorization : Basic Adgasgasg=
```

- 인코딩은 암호화가 아니기에 이 방식은 HTTPS와 같이 암호화된 통신에서만 사용한다.
- 아이디와 패스워드를 서버에서 DB조회 + 비즈니스 로직으로 인증/인가 확인 -> 서버 자원 부담이 된다.
- 구현이 상당히 간단하다.

### 2. Digest Authentication (죽은 기술)
- 비밀번호를 직접 담아보내지 말고 해시 값으로 변환해서 보내는 방식
- Nonce ,Realm
    - Nonce : 서버가 클라이언트한테 한 번만 쓰라고 주는 일회성 난수
    - Realm : 서버가 관리하는 보안 공간의 범위를 표기하는 문자열 (users , posts)

#### 실행 과정
1. 클라이언트가 보호된 리소스 요청
2. 서버가 Nonce, Realm을 전송 (401응답)
3. 클라이언트가 비밀번호 + Nonce , Realm을 해시 함수로 구워서 Authorization 헤더에 보냄.

#### 특징
- 보안성이 올라감.
- 매 요청마다 난수 만들고 기억하고 오면 해시화해서 확인하여 서버 cpu비용이 커짐.

### 3. Bearer Token 방식

```
Authorization: Bearer mF_9.B5f-4.1JqM
```

- 이 토큰을 소지한 요청은 "인증,인가"된 것으로 한다.
- 유저의 아이디와 비번은 최초 로그인 할 경우에만 전송됨.

#### 실행과정
1. 최초 로그인 
2. 서버에서 인증을 수행하고
3. 토큰을 발급 후 클라이언트에게 전송
4. 클라이언트는 인증/인가가 필요할 때, 서버에 토큰을 전송함.

#### Bearer token 이란?
- Bearer : 소지자 , 운반인
- 토큰을 들고 있는 사람은 정당한 권한이 있는 것으로 생각
- 토큰을 전송한 클라이언트가 진짜 토큰의 주인인지 아닌지 상관없음 (위조만 아니라면 그냥 통과)

장점 
1. 유저의 비밀번호가 보호됨.
2. 범용성이 좋다
    - 과거의 인증 방식 (Session + Cookie) -> 브라우저에는 잘 작동하지만 모바일에서는 동작하지 않는다.
    - 도메인이 달라지면, 쿠키가 따라 붙지 않는다.
3. CSRF 방지

단점
1. 토큰이 탈취당하면 위험함.
    - 토큰은 탈취당하기 쉽다 (클라이언트 관리)
    - 방지하기 위한 방법
        a. HTTPS <- 동작하는게 기본인 원칙
        b. 토큰은 유효기간을 상당히 짧게 설정하는게 일반적
            - 제공 서비스마다 설정하는 유효기간이 다름. 
            - 서비스마다 지켜야하는 정보의 수준이 다름.
    - 토큰은 보관하기 까다로움.
        a. 브라우저 <- 자바스크립트로 Storage 접근 가능
        b. 브라우저의 저장공간은 2가지
            i) Storage : 자바스크립트로 값을 가져올 수 있음.
            ii) Cookie : 항상 모든 요청에 쿠키가 자동으로 붙은
        c. Storage에 보관하면 XSS 스크립트 해킹으로 토큰 탈취
        d. Cookie에 보관하면 CSRF 공격에 취약함.
2. Bearer Token의 한계
- 오페이크 토큰 , 불투명 토큰 : 토큰 값이 의미없는 토큰 (무작위 문자열)
- 서버에는 이것을 보관해야함.
- 토큰을 조회할 때 리소스를 사용

- 서버가 DB를 조회하지 않아도 토큰에 유저 정보가 적혀있고 , 정보위조가 되지 않았는지 스스로 증명할 수 있으면 좋겠다. -> JWT 

### JWT (JSON Web Token)

- 당사자 간 정보를 JSON 객체로 안전하고 가볍게 전송하기 위한 웹 표준 개방형 규격
- 기존 토큰의 무작위 글자가 아니라 인증정보를 서버에서 서명해서 만들어진 토큰
- 인증 + 서버의 서명

#### JWT 구조
- HEADER.PAYLOAD.SIGNATURE 
    - Header, Payload는 Base64 인코딩
    - Signature는 위의 내용을 해시화 + 키

1. Header
- 토큰의 타입, 서명에 사용된 알고리즘
- 알고리즘 안쓰면 뚫리기도 함 (? 왜? )

```
{
  "alg": "HS256",
  "typ": "JWT"
}
```

2. Payload

```
{
  "email": "void@startupcode.kr",
  "username": "void",
  "iat": 1609239023,
  "exp": 1609242623
}
```

- JWT 토큰에 담을 정보
- 평문이기에 노출되면 안되는 값을 넣으면 안됨.
- iat : 토큰이 발행된 시간 (Timestamp)
- exp : 토큰 만료시간 (Timestamp)

3.Signature 
- 토큰이 위조 되었는지를 확인하는 영역
- 인토딩 헤더 + 인코딩 페이로드 + 서버만 알고 있는 비밀 키 값 => 하나로 합쳐서 암호화

#### 특징

1. 완전한 stateless -> 확장성
2. DB 조회를 상당히 적게 한다.
    - 데이터베이스는 가장 느린 쓰기 장치에 기록됨. 그래서 병목현상의 주요지점.
    - 요청이 늘어나도 JWT 검증 시간만 늘어남.

3. 무효화가 어려움.
    - JWT 토큰 발급되는 순간 어디있는지 모름.
    - 해커가 JWT 토큰했을 때, 만료시키고 싶어도 못함.
    - 방지
        - Access Token , Refresh Token
4. 네트워크 대역폭 낭비
    - 토큰은 내부 내용이 많을 수록 길이가 길어짐.
    - 옵저빌리티 해보면 알 수 있음.
        - JWT 크기가 1kb정도로 가정
        - 유저 한명이 1분에 300 ~ 500개 api 요청함.
        - MAU가 만명일 경우 1kb * 500 * 10000 = 5TB

- 보안성과 편의성의 딜레마
    - 보안성을 높이면, 편의성이 떨어짐
    - 편의성이 높으면, 보안성이 떨어짐
    => Access Token, Refresh Token

#### Access Token , Refresh Token

Access Token 
- api 리소스에 접근하기 위한 신분증
- 15분 ~ 30분
- 프론트엔드 메모리 or LocalSorage or HttpOnly 쿠키에 저장
- 매 api 요청에 보냄

Refresh Token
- AccessToken을 발급하기 위한 인증서
- 2주 ~ 1달
- 
- Access Token이 만료되었을 때 한번만 보냄.

Refresh Token이 탈취당하면?
- 이 문제를 해결하기 위한 기술이 RTR

#### RTR (Refresh Token Rotation)
- Refresh Token 재사용하지 말자 (뭐야 그럼 로그인 유지하는 기능은 이것을 사용하지 않는건가? 아니면 사용하는데 기한이 있는거였나?)

해커가 탈취한 경우 -> Reuse Detection
1. 해커가 훔친 R1 토큰으로 새 토큰 요청 (R = Refresh Token)
2. 서버 R1 지운다. 해커한테 새토큰세트(A2,R2)를 준다. (A = Access Token)
3. R2를 저장소에 저장
4. 진짜 유저가 R1 토큰으로 재발급 요청
5. R1으로 발급된 유저는 비정상 유저임을 확인 할 수 있음. (? softDelete여서 확인할 수 있는건가?)
6. 발급한 Refresh Token들을 무효화함.

의문 : 해커 탈취한 경우 4,5번 과정에서 진짜 사용자가 R1로 재발급 요청을 한다고 어떻게 R1으로 발급된 유저는 비정상 유저임을 어떻게 확인 할 수 있는가요? R1은 이미 지워져서 없는데. softDelete로 구현하기 때문인가요? 아니면 진짜 사용자가 로그인을 통해서 알 수 있는건가요?

탈취되고 진짜 사용자가 로그인을 하면 refreshToken을 재생성하니까 탈취된지 모르는거 아니야? -> 그래서 로그인시 기존 토큰들은 삭제함.

결국 사용자가 해당 서버를 자주 이용해야 탈취를 파악할 수 있는데 그럼 로그인을 오랬동안 안하면 탈취 된지 몰라서 휴먼계정이라는 것이 생긴건가요?

### Layered Architecture

#### 데이터베이스와 객체지향의 구조 차이

- 테이블을 자바에서 쓰려니까 객체 지향, 관계 지향이 다르다.
- 데이터베이스의 규칙을 객체지향코드에서 사용하기 위해
- RDB 테이블 구조와 규칙을 객체화 -> Entity = 테이블 정의 + 컬럼 매핑 + 키 정의

- 트랜젝션의 책임
1. 두개 이상의 테이블을 다룰 경우 = service
2. 한 개의 테이블을 다룰 경우 = repository
