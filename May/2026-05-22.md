## 3. 키워드 별 딥다이브

- HTTP
    - 2차 키워드 TLS(Transport Layer Security)
        
        출처 https://www.cloudflare.com/ko-kr/learning/ssl/transport-layer-security-tls/
        
        - TLS는 인터넷 상의 커뮤니케이션을 위한 개인 정보와 데이터 무결성을 제공하는 보안 프로토콜
        - 주로 사용되는 것
            - 웹 사이트를 로드하는 웹 브라우저와 같이 웹 애플리케이션과 서버 간의 커뮤니케이션을 암호화하는 것
            - 이메일, 메시지, VoIP 등 다른 커뮤니케이션을 암호화하기 위해 사용
        - TLS는 SSL이라는 암호화 프로토콜에서 발전한 것 즉, SSL → TLS
        - HTTPS는 HTTP 위에 TLS를 구현한 것임.
        - 암호화 , 인증 , 무결성을 제공함.
        - TLS를 사용하기 위해서는 origin server에 TLS 인증서가 설치되어 있어야함.
        - 인증기관(CA)이 인증서를 발급 (알지? 뭐 인증서에는 서버 공개키와 인증정보가 들어있고)
        - TLS handshake
            - 사용할 TLS version 지정, 사용할 암호 제품군 결정, TLS 인증서를 사용하여 서버의 신원 인증 → handshake 완료 후 키 간의 메시지를 암호화하기 위한 세션 키(대칭 암호화 키)를 생성. (이거 전달 과정은 배웠으니 pass)
            
            ![image.png](attachment:4b303db1-1471-4298-a7f4-bd74011345f0:image.png)
            
        - 최신 버전 TLS는 웹 APP에 성능 영향 거의 없음.
            - TLS handshake가 완료되기 전에 서버와 클라이언트가 데이터 전송을 시작하도록 하는 TLS False Start
            - 이전에 커뮤니케이션한 적이 있는 서버와 클라이언트가 간략화된 핸드셰이크를 사용하도록 허용하는 TLS 세션 재개
            - TLS 1.3은 더 빠름. TLS handshake가 2회 왕복에서 1회 왕복으로 됨. ㅌ
    - 2차 키워드 클로킹
        - 검색 엔진 최적화 (SEO) 기법 중 하나, search engine spider(web crawler)에게 표시되는 콘텐츠와 사용자의 브라우저에 표시되는 콘텐츠를 다르게 하는 기법임.
        - 사용자의 ip주소나 User-Agent HTTP Header를 기반으로 콘텐츠를 전달함.
        - 검색 엔진을 속여서 보이면 안되는 페이지를 보이도록 할 수 있게함. (black hat SEO)
        - Adobe Flash와 같은 non-textual container는 검색엔진이 정보를 찾을 수 없기에 클로킹으로 알릴 수 있기도함 (구식방식) → 좀 더 기술이 발전하여 SEO에 클로킹이 필요 없어짐.
        - 검색 엔진이 사이트 순위를 높이도록 유도하는 [spamdexing](https://en.wikipedia.org/wiki/Spamdexing) 기법으로 자주 사용함 → 이거 범죄 아닌가?
        - [doorway page](https://en.wikipedia.org/wiki/Doorway_page) 기법의 한 형태
        - DMOZ web direcory에도 사용하긴 하지만 이것은 인간 편집자를 속이기 위한 방식
        - 판단 기준
            - HTTP Referrer : 사용자가 어디에서 링크를 클릭하고 왔는지 알려줌.
            
            ```html
            Referer: https://google.com
            ```
            
            - User-Agent : 브라우저나 프로그램 정보
            
            ```html
            User-Agent: Googlebot
            ```
            
            - IP 주소 : IP 대역을 확인하여 구분 (좀 더 정교한 것은 HTTP 요청의 총량 , 순서 , 요청지연시간, robots.txt 파일 등으로 확인
    - HTTP caching https://developer.mozilla.org/ko/docs/Web/HTTP/Guides/Caching
    - 영어 문서랑 한국어 문서랑 달라서 좀 오락가락함.
        - 사설 브라우저 캐시 : 단일 사용자 전용 , HTTP를 통해 다운로드된 모든 문서들을 가지고 있음.
        - 공유 프록시 캐시 : 한 명 이상의 사용자에 의해 재사용되는 응답을 저장하는 캐시 , 조회가 많이 되는 리소스를 재사용하여 트랙픽과 latency를 줄임
        - HTTP 캐시는 일반적으로 GET에 대한 응답만 캐싱함.
        - 캐싱 제어
            - Cache-control Header (HTTP /1.1) : 캐싱 정책을 정의함. ( no-store, no-cache ,private , public 등)
            - Pragma Header (HTTP/1.0) : Cache-Control 해더가 없을 경우에만 사용 → 아직 HTTP / 1.0을 사용하는 곳들과 통신하기 위함인 듯.
        - 유효성
            - 만료시간 이전에는 유효(fresh) , 만료 이후는 실효(stale) → 예상 외로 실효 리소스는 축출(eviction)되거나 무시되지는 않는다. 실효된 리소스는 [`If-None-Match`](https://developer.mozilla.org/ko/docs/Web/HTTP/Reference/Headers/If-None-Match) 과 함께 보내져서 실효되었는지 확인된다.
            - “Cache-control Header” 나  “Expires Header에 Date Header의 값을 뺀 결과값” 을 봐서 유효 수명을 알 수 있음.
            - 서버가 명시적으로 유효성을 지정하지 않으면 휴리스틱으로 유효 시간을 추정함.
            - 리비전된(Revved) 리소스 (?)
                - 캐시된 리소스가 많을 수록 웹 사이트의 응답성과 성능은 좋아짐. → 만료시간이 길면 오래 저장할 수 있음. → 하지만 업데이트가 어려움 ( 기본적인 리소스들이라 다른 많은 코드와 얽혀있어서 어려운 듯)
                - revving이라는 기술로 해결
                    - 드물게 업데이트되는 파일들을 특정한 방법으로 이름을 붙임.
                    - 새로운 버전을 가지기 위해, 해당 리소스와 연결된 모든 것들을 변경해야함.
        - 캐시 검증
            - Cache-control: must-revalidate를 포함할 경우 발생함.
            - ETags
                - 강한 검증으로 사용할 수 있는 것
                - 사용자에게 있어서 불투명한 값
                - 이 값을 받은 이후에는 요청 헤더 내에 [`If-None-Match`](https://developer.mozilla.org/ko/docs/Web/HTTP/Reference/Headers/If-None-Match) 를 넣을 수 있음.
            - Last-Modified
                - 약한 검증에 사용 (1초의 해상도만 가질 수 있기에 약하다고 간주 ? 뭔소리야?)
                - 이 값을 받은 후에는 요청 헤더 내에 [`If-Modified-Since`](https://developer.mozilla.org/ko/docs/Web/HTTP/Reference/Headers/If-Modified-Since) 를 넣을 수 있음.
        - 상황에 따른 응답
            - Vary
                
                ```html
                Vary: User-Agent
                ```
                
                - 서버로부터 새로운 리소스를 요청해야 하는지, 캐시된 응답이 사용될 수 있는지를 결정하기 위해 이후의 요청 헤더를 대조하는 방식을 결정 → 쉽게 말하면 vary에 지정한 header field를 보고 캐싱을 하라는 것 (의문 : 근데 왜 이렇게 분리했지? 그냥 해더 값보고 알아서 하면 안되나?)
                - 캐시의 효과를 떨어뜨리기 쉬움. 정규화를 거쳐야함.
                - 데스크탑과 모바일 사용자에게 다른 컨텐츠를 제공하거나 클로킹 의도가 없다고 알려주는데에 유용함.
    - 교차 사이트 요청 위조 (CSRF)
        - https://developer.mozilla.org/ko/docs/Glossary/CSRF
        - 정의 : 신뢰할 수 있는 사용자를 사칭해 웹사이트에 원하지 않는 명령을 보내는 공격
            - 예 : URL 뒤에 악성 매개변수를 포함하는 방식
            
            ```html
            <img src="https://www.example.com/index.php?action=delete&id=123" />
            ```
            
    - 크로스 사이트 스크립팅 (Cross-site scripting / XSS )
        - https://developer.mozilla.org/ko/docs/Glossary/Cross-site_scripting
        - 정의 : 공격자가 웹사이트에 악성 클라이언트 스크립트를 삽입할 수 있도록 하는 보안 취약점 공격 → 다른 사용자가 이것을 작동시키면 그 사용자가 피해를 입는 방식
        - 사용자의 브라우저가 신뢰할 수 없는 악성 스크립트를 탑지할 수 없고 쿠키,세션 토큰 등 민감한 정보에 대한 접근 권한을 부여해버리거나 , HTML 콘텐츠를 작성 할 수 있도록함. (? 그럼 스크립트를 눌러도 세션토큰이 탈취되는 거니까 공격자가 로그인도 막 할 수 있는건가? 되게 위험한데? 게시판 만들때 이것도 고려해야하나 )
    - HTTP Cookie
        - 세션관리 , 개인화 , 트래킹을 목적으로 사용
        - 지금은 modern storage APIs를 사용해 정보를 저장하는 것을 권장함. (모든 요청마다 쿠키가 전송되기에 이를 해결하는 방식)
        - Set-Cookie Header
            
            ```html
            Set-Cookie: <cookie-name>=<cookie-value>
            ```
            
            - 이를 클라이언트가 저장하고 요청할 때 넣어서 보냄.
        - 쿠키의 lifetime
            - 세션 쿠키 (`Expires`, `Max-Age` 속성이 없는 쿠키)는 현재 세션이 끝날 때 삭제됩니다. 브라우저는 "현재 세션"이 끝나는 시점을 정의하며, 어떤 브라우저들은 재시작할 때 세션을 복원해 세션 쿠키가 무기한 존재할 수 있도록 합니다.
            - 쿠키 만료 시점을 설정할 때 만료시점은 쿠키가 저장되는 클라이언트 시간을 기준으로 함.
        - Secure , HttpOnly 쿠키
            - Secure 쿠키는 HTTPS의 암호화된 요청일 경우에만 전송함. (그래도 민감한 정보는 절대로 쿠키에 저장하면 안됨. 본질적으로 안전하지 않음)
            - XSS를 막기위해 HttpOnly 쿠키는 JavaScript의 [`Document.cookie`](https://developer.mozilla.org/en-US/docs/Web/API/Document/cookie) API에 접근 불가 (이유 : 서버의 세션 쿠키는 JavaScript)를 사용할 필요가 없어서)
        - 쿠키의 스코프
            - Domain은 쿠키가 전송되게 될 호스트들을 명시함.
            - Path는 쿠키헤더를 전송하기 위해 요청된 URL내에 반드시 존재해야하는 URL 경로
            - SameSite 쿠키 : 쿠키가 cross-site 요청을 막아서 CSRF에 대해 보호방법을 제공함. (아직은 실험중이며 모든 브라우저에 의해 제공되고 있지는 않음)
        - 보안
            - 세션 하이재킹과 XSS
            - Cross-site 요청 위조 (CSRF)
        - 트래킹과 프라이버시
            - 서드파티 쿠키
            - Do-Not-Track
            - EU 쿠키 디렉티브
            - 좀비 쿠키와 Evercookies
            

## 4. 주제로 복귀

- HTTP의 Stateless 특성이 요청 처리 구조와 서버 확장성에 미치는 영향을 분석하시오.
- stateless는 키오스크처럼 이용자의 정보를 기억하지 않는다는 것이다. 이러한 특성 덕분에 client request를 받으면 처리해서 응답만 반환하면 되고 단순한 요청 처리 구조를 가지고 있어서 정보교환이 빠르고, 하나의 실패가 다른 요청들에 영향을 크게 미치지 않다. 하지만 이러한 특성 때문에 이용자의 정보를 알기 위해서 쿠키를 사용하게 된다.
- 또한 stateless하기에 서버 확장성이 높다
- 어떠한 서버도 사용자의 정보를 저장하지 않기 때문에 어느 서버에서 요청을 처리해도 문제가 없고 이는 여러 서버를 수평확장(Scale-Out)하기 쉬워진다.
