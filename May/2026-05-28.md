## 새로 배운 내용
### NoSQL

- Not only SQL,
SQL만을 사용하지 않는 여러 유형의 데이터베이스
- 데이터의 다양성, 대규모 데이터 처리, 수평 확장 및 유연한 설계 요구에 대한 필요성이 점점 증가하고 있음.

RDB의 한계
- 정규화된 테이블 구조 -> 유연하지 못함
- 트랜잭션 => 동시 처리성이 낮음
- 디스크 기반으로 영원히 저장 => 확장성이 낮음

#### 1. Key-value Store
- 보이는 것처럼 key-value형식으로 저장

- 매우 빠른 읽기/쓰기 속도 (해시 테이블 기반의 인메모리 구조)
- 구조단순, 수평 확장 용이함.
- 복잡한 쿼리나 검색이 어려움
- 데이터 구조가 단순해서 value 내부 구조를 DB가 이해하지 못함. (?왜)
- 주로 세션,캐시,토큰 등으로 사용함 (읽고 쓰기가 장점인 만큼 읽고 쓰기가 자주 발생하는 곳에 사용함.)

##### In-Memory

CPU : 연산처리하는 부품 , 연산 처리하기 위해 데이터를 빠르게 가져와야함.

Memory : 연산에 사용할 수 있도록 HDD 데이터를 로드하는 속도는 빠르지만 휘발성있음.

Disk : 데이터를 반영구적으로 보관할 수 있지만 물리적 한계로 인해 속도가 느림
(원판이 돌아서 저장하기 때문에 원판이 돌아가는 만큼 무조건 시간이 걸림.)


##### 저장장치 종류
HDD : 물리적 디스크에 기록
- 디스크를 회전시켜서 기록함 
- 30~~150MB/s , 24원/1GB

SSD : 낸드 플래시에 기록
- 반도체 칩 전자회로에 저장 (반영구적)
- 7500MB/s , 115원/1GB

RAM : 트랜지스터 + 커패시터
- 커패시터에 전하를 통해 데이터를 표현 (휘발성)
- 25000MB/s
- 5400원/1GB

1. Key-Value store
- Key-value 데이터베이스
- SSD를 사용함
- 예) Redis

2. Document Store
- JSON, XML 같은 문서 단위로 데이터 저장
- 스키마 변경이 유연
- 쿼리 검색 유연
- 데이터 간 관계성이 약함.
- 예) MongoDB , CounchDB

3. Column-Oriented Store
- 테이블 구조처럼 컬럼 단위 데이터 저장, 동일 행 내 컬럼 그룹 관리
- 대용량 데이터,빅데이터 분석에 적합
- 설계가 복잡함
- 자연스럽게 행 조회는 느리기에 컬럼 단위로 저장되기에 쓰기가 번거로움.
- 주로 로그수집 , 분석 , 시계열 데이터와 같은 곳에 유용함.
- 예) Apache Cassandra

row-oriented store = RDB
- 행들을 읽고 값을 꺼내서 계산 -> 특정 열만 관심있을 때, IO 느림

column-oriented store != RDB
- 검색된 열만 읽고 값을 꺼내서 계산 -> 특정 열만 관심있을 때, IO 빠름

4. Graph Store
- 노드와 엣지 구조로 데이터를 저장함.
- 관계 기반 조회 최적화 
- 트랜잭션/대용량 처리 복잡
- 관계를 신경써야해서 수평확장이 어려움. 
- SNS 친구 시스템, 추천 시스템에 효율적
- 예) Neo4j

### 데이터베이스 확장

#### 파티셔닝 

- 기존 테이블을 나누는 방식

1. Vertical Partitioning
 (테이블의 컬럼을 나누자) 
- 자주 조회되는 컬럼 아닌 컬럼 불리하자
- 조회가 잦은 데이터에 대한 IO 감소
- Transaction할 때 독립성을 지키기위해 테이블을 수정하고 있으면 다른 곳에서 접근하지 못하는데 테이블이 크면 하나만 수정해도 전체에 접근하지 못해서 낭비가 큰데 분리함으로써 효율 증가
- 조인 필요도가 늘어서 쿼리 복잡도가 증가함
- 2개 테이블 동시 적용 트랜잭션시 어려움

2. Horizontal Partitioning
- 하나의 스키마를 여러 테이블로 저장
- 날짜별 , 지역별 등등 범위에 따라 분리
- 쓰기 성능 증가 + 파티션 별로 처리하긴 좋음 + 아카이빙, 백업이 쉬움.
- 인덱스 관리 힘듬 + 데이터 불균형 + 쿼리 검색 어려움 + 트랜잭션 어려움

#### 복제(Replication)
- 똑같은 데이터를 복제하다.
- Master , Slave로 구분 (미국은 Slave에 민감해서 다르게 표현하긴함 ㅋㅋㅋㅋ)
- Master은 쓰기 전용 , Slave는 읽기 전용

- 발생한 모든 변경 사항은 이진 로그에 순서대로 기록
- Master의 이진 로그를 읽어 변경 사항을 동일하게 반영합니다.

#### Server Cache
1. Local Cache
- 인스턴스에 독립적 존재
- 데이터 접근 빠르고 네트워크 지연 없음
- 수평적 확장시 일관성 유지가 힘듬
- 각 서버 캐시가 독립적

2. Global Cache
- 여러 인스턴스(WAS)에서 공유하는 캐시
- 데이터 일관성
- 네트워크 지연 가능성

=> 당연한거 가깝고 분리 되어있으면 빠른 대신 독립적이여서 일관성이 유지되지 못하고 멀고 중앙형식이면 중복은 없지만 느리지.

spring local cache를 적용하는 것을 과제할 때 생각해 봐라. (예시 - 인기글)

캐싱 기법 적용
- DB 엔진 메모리
- 로컬 브라우저
- 스토리지 (Cloudfront)
- 프록시 (Nginx Microcache) 
=> 웹 캐시 (브라우저 , 프록시 , CDN)

##### Storage

- HTTPS를 사용하지 않는 신뢰할 수 없는 출처에서는 CacheStorage가 항상 SecurityError로 거부함.
- Cache Storage API 작업은 비동기방식

##### Proxy
- HTTP 1.1 기반
- HTTP 요청을 수신하면 메모리에서 Cache Index를 확인함.
- 있으면 응답하고 없으면 서버로 요청 전송 
- 사실 있다고 무조건 응답하는 것이 아니라 HTTP Header를 보고 결정함 
    - (client) Cache-Control: no-store => 캐싱하지마
    - (server) Cache-Control: max-age=3600 => 1시간 동안 캐싱 가능
- 캐시로 요청에 응답했으면 Cache Index 갱신
