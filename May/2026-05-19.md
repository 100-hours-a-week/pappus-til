# 주제 1: Servlet과 Servlet Container

## Servlet이란?

Servlet은 Java에서 HTTP 요청(Request)과 응답(Response)을 처리하기 위해 사용하는 기술이다.

과거에는 개발자가:
- HTTP 요청 문자열 분석
- 응답 헤더 생성
- 응답 포맷 작성

등을 직접 처리해야 했지만,

Servlet이 등장하면서:
- HTTP 처리 부분을 Servlet이 대신 담당
- 개발자는 비즈니스 로직에 집중 가능

해졌다.

즉:

```text
HTTP 처리 = Servlet
실제 기능 구현 = 개발자
```

---

## Servlet이 지원하는 기능

- HTTP 요청 처리
- HTTP 응답 생성
- 요청/응답 객체 제공
- URL 요청 처리
- 라이프사이클 관리

---

## 개인적인 비유

Servlet은 은행 창구와 비슷하다.

예시:
- 고객(Client)이 요청
- 은행원(Servlet)이 요청 내용을 처리
- 내부 시스템(비즈니스 로직)과 연결
- 결과 응답

즉:
개발자는 HTTP 프로토콜 세부사항보다 실제 서비스 로직에 집중할 수 있다.

---

## 의문

### 요청 하나당 Servlet 하나를 만들면 너무 많아지는 것 아닌가?

맞다.

URL마다 Servlet을 직접 만들면:
- 관리 어려움
- 중복 증가
- 유지보수 어려움

문제가 발생한다.

이를 해결하기 위해 Spring MVC 같은 구조가 등장하였다.

---

# Servlet Container

## 역할

Servlet을 관리하는 컨테이너이다.

Spring의 Bean Container와 느낌이 비슷하다.

공통점:
- 객체 생성
- 객체 관리
- 생명주기 관리

를 수행한다.

---

## Servlet Container 기능

- Servlet 객체 생성
- Servlet 초기화
- 요청마다 적절한 Servlet 실행
- 종료 시 메모리 정리
- 멀티 스레드 기반 요청 처리

---

## 대표적인 Servlet Container

- Apache Tomcat
- Jetty

# 주제 3: Spring MVC 구조

# Spring MVC란?

MVC 패턴을 웹 환경에 맞게 확장한 프레임워크 구조이다.

특징:
- MVC 패턴 기반
- 여러 디자인 패턴 포함
- Front Controller 패턴 사용

---

# Spring MVC 전체 흐름

```text
HTTP 요청
   ↓
DispatcherServlet
   ↓
HandlerMapping
   ↓
HandlerAdapter
   ↓
Controller(Handler)
   ↓
ViewResolver or HttpMessageConverter
   ↓
HTTP 응답
```

---

# 1. DispatcherServlet

## 역할

Spring MVC의 Front Controller

---

## 특징

- 모든 요청을 가장 먼저 받는다.
- 요청 흐름 전체를 관리한다.
- 적절한 Controller에게 요청 전달

---

## 핵심 느낌

"교통정리 담당"

---

## 중요

DispatcherServlet은:
- MVC 구성요소 자체라기보다
- Spring MVC 전체를 연결하는 핵심 인프라

느낌이다.

---

# 2. HandlerMapping

## 역할

요청 URL에 맞는 Handler 탐색

---

## 예시

```text
/users → UserController
/posts → PostController
```

"어떤 Handler를 실행할지 찾는 역할"


# 3. HandlerAdapter

## 역할

Handler 실행 방식 통합

---

## 왜 필요할까?

Handler 종류마다 실행 방식이 다를 수 있기 때문이다.

예시:
- 과거 Controller 방식
- @RequestMapping 방식
- HttpRequestHandler 방식

등이 존재한다.

---

## 핵심 느낌

Handler를 실행 가능하도록 중간에서 맞춰주는 어댑터

---

# 의문 : Handler과 Controller는 어떠한 관계인가?

## Handler 안에 Controller가 포함된다.

즉:

```text
Handler ⊃ Controller
```

관계이다.

Controller는 Handler의 한 종류이다.

---

# 4. ViewResolver

## 역할

논리적인 View 이름을 실제 View 파일로 변환

---

## 예시

```java
return "home";
```

↓

```text
/templates/home.html
```

---

## 핵심

Controller는:
- 실제 파일 경로를 직접 반환하지 않는다.

ViewResolver가:
- 실제 파일 위치를 찾아준다.

---

# 정적 파일은?

css/js/image 같은 정적 파일은:

```text
ResourceHandler
```

가 직접 처리한다.

따라서:
- ViewResolver를 거치지 않을 수도 있다.

---

# Controller 종류

# 1. 기존 Controller 방식

```text
Controller
→ 논리적 View 이름 반환
→ ViewResolver
→ HTML 응답
```

예시:
- JSP
- Thymeleaf

---

# 2. RestController 방식

```text
RestController
→ 객체 반환
→ HttpMessageConverter
→ JSON 변환
→ 응답
```

---

# 의문 : ViewResolver는 JSON을 반환하지 못하는데 HttpMessageConverter는 같은 위치라고 생각해도 될까?

어느 정도 맞다.

둘 다:
- Controller의 반환값을 최종 응답 형태로 변환한다.

---

## 차이점

| 구성 요소              | 역할               |
|----------------------|--------------------|
| ViewResolver         | View 파일 처리       |
| HttpMessageConverter | JSON/XML 데이터 처리 |

---

# Spring MVC 역할 정리

| 역할 | Spring 구성 요소 |
|---|---|
| Controller | Controller |
| Model | Service / Repository |
| View | HTML / JSON |
| 인프라 | DispatcherServlet / HandlerMapping / ViewResolver |

# 주제 4: HTTPS와 TLS

# 과거 HTTP 환경

초기의 Web
- 정보 공유 목적
- 공개되어도 큰 문제가 없는 데이터가 많았다.

즉, 보안 중요성이 크지 않았다.

---

# 현대 Web 환경 변화

현재는:
- 로그인
- 결제
- 송금
- 인증서
- 개인정보

등 민감한 데이터가 많아졌다.

즉, 보안이 매우 중요해졌다.

---

# HTTPS

## 정의

```text
HTTPS = HTTP + Secure(TLS)
```

- HTTP 위에 TLS 보안 계층을 추가한 것이다.

---

# HTTPS 핵심 요소

# 1. 암호화

데이터를 안전하게 보호하는 기술

---

# 대칭키 , 비대칭키 암호화

## 특징

대칭키 : 같은 키로 암호화/복호화 (빠르지만 / 키 전달이 어려움)
비대칭 키 : 공개키 / 개인키 사용 (키 교환이 안전하지만 / 연산량이 많아 처리속도가 느리다.)

---

# 비대칭키 활용 방식

## 1. 공개키 암호화 → 개인키 복호화

- 데이터 암호화

---

## 2. 개인키 암호화 → 공개키 복호화

- 전자 서명

---

# 2. 인증(Authentication)

- 통신 상대가 진짜인지 확인

---

# CA(Certificate Authority)

- 인증서를 발급하는 기관

---

# HTTPS 통신 과정

1. 서버가 공개키 / 개인키 생성
2. 서버가 - 공개키 + 서버 정보를 CA에 전달
3. CA가 인증서 발급 (인증서 구성 = 서버 공개키 + 서버 정보 + CA 정보 + CA의 전자 서명)
4. Client가 서버에 인증서 요청
5. Client가 인증서 검증 (브라우저 내부에 CA 목록 , CA 공개키 저장되어 있음 / 예시 chrome://certificate-manager/crscerts)
6. Client가 대칭키 생성 후 서버 공개키로 암호화하여 서버에 전달.
7. 이후 통신은 대칭키 사용 (대칭키가 빠르기에 통신에는 대칭키 사용)

# 핵심 정리

```text
비대칭키
→ 안전한 키 교환

대칭키
→ 실제 데이터 통신
```

HTTPS는:
- 비대칭키의 안전성
- 대칭키의 속도

둘 다 활용한다.

# 오늘의 회고

오늘은 Spring MVC 흐름을 학습하면서 단순히 Controller만 사용하는 것이 아니라 내부적으로 수많은 구성 요소들이 함께 동작한다는 것을 알게 되었다.

예전에는 "요청 들어오면 Controller 실행" 정도로만 생각했는데,

실제로는 요청 분석 -> Handler 탐색 -> 실행 방식 통합 -> 응답 변환
과정이 모두 존재한다는 것을 이해하게 되었다.

그리고 Handler와 Controller의 관계도 헷갈렸는데,

```text
Handler ⊃ Controller
```

라는 개념으로 이해하니 정리가 잘 되었다.

HTTPS도 단순히 보안이 적용된 HTTP정도로만 알고 있었는데

- 공개키
- 개인키
- 인증서
- 전자서명
- 대칭키 교환
- TLS

등 여러 기술이 함께 사용된다는 점이 인상 깊었다.
특히 대칭키 , 비대칭키가 서로의 단점을 HTTPS가 보완해서 사용한다는 점이 흥미로웠다.

오늘 학습을 통해
- Spring MVC 요청 흐름
- Servlet 구조
- DispatcherServlet 역할
- HTTPS 암호화 방식

등 웹 백엔드 핵심 개념을 이전보다 훨씬 구조적으로 이해할 수 있었다.
