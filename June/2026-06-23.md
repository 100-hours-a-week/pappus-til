## 새로 배운 내용
### EFS
- AWS에서 제공하는 네트워크 파일 시스템(NFS)
- 사용자가 스토리지를 직접 설정하거나 용량을 관리하지 않아도 자동으로 확장,축소되고 운영이 자동화됨.
- 여러 EC2에 동일한 환경변수가 필요할 때 사용(.env, key)

마운트
- 외부 파일 시스템을 서버의 특정 디렉토리에 연결해서, 로컬 폴더처럼 사용하는 작업
- 예) EC2 A Instance에 EFS나 EBS를 마운트한다. 


1. 여러 서버가 같은 파일을 공유 해야할 때
2. 용량을 예상할 수 없을 때
3. 여러 가용영역(AZ)에서 공유 해야할 때
- Regional EFS
- 같은 region 안에 여러 AZ에 데이터를 중복 저장하는 방식
- 가용성이 상당히 높아짐

#### EFS 구성요소
1. 파일 시스템
2. Mount Target
- EC2가 VPC 안에서 EFS에 접속하기 위한 네트워크 진입점
- EFS는 VPC 안에서 접근해야함. (당연히 보안을 위해서 private network안에 넣는 느낌)
- Gateway랑 비슷하다고 생각함.
3. Security Group
- VPC 내부에서 통신하기 위해 보안 그룹을 설정해야함.

#### EFS,EBS,S3
- EBS: 서버 한 대의 디스크
- EFS: 어러 서버가 공유하는 파일 시스템
- S3: 객체 저장소

#### EFS 성능 및 비용
- 네트워크 통신의 과금 구조기에 성능을 조정하여 비용을 줄이는 것이 좋음.

##### 1. 성능 모드
- EFS, 일반 설정으로 시작하고 사용하면서 모니터링을 통해서 성능을 최적화하는 것이 좋다.
- 보통은 General Purpose를 추천

- General Purpose: 낮은 지연 중심
- Max I/O: 높은 병렬 처리 중심

##### 2. Throughput Mode
- Elastic: 사용량에 따라 처리량 조정
- Bursting: 버스트 크레딧 특성을 활용
- Provisioned: 필요한 처리량을 직접 지정

##### 3. Lifecycle Management
- 오랫동안 접근하지 않는 파일은 저렴한 스토리지로 이동시키는 것을 고려해야함. (어느정도 자동화 되어있긴 함.)
- RAM,SSD,DISK순으로 가격이 싸기에 접근이 덜 되는 파일은 DISK로 이동

##### 고려사항
- EFS는 상대적으로 비싼 저장소기에 공유파일 꼭 필요하지 않으면 사용하지 않는것이 좋음
- DB 디렉토리로는 사용하지 않는게 좋음. 그냥 EBS에서 사용해라
- NFS Port 2049를 인터넷에 열면 공공재가 되어버림.
- AWS에서 제공하는 많은 서비스는 기본적으로 백업을 제공하지만, EFS는 백업에 대해서 설계해야함.
- AWS Backup 정책 읽어봐라.

### S3
- S3는 이미지, 동영상, 백업파일 등 많은 파일을 객체단위로 저장하는 객체 스토리지 서비스
- Simple Storage Service

- 이미지 저장같은 경우, EBS를 사용하면 각 Instance만 보고 있어서 공유자원이 아님. 
- EFS로 사용하기에도 외부에서 이미지를 볼 수 있어야 할 때 사용할 수 없음.
- 그래서 이때 S3를 사용하게 됨.
- HTTP, AWS SDK를 통해서 접근함.

#### 객체 스토리지
- Bucket: 객체를 담는 곳
- Key: 객체 고유 경로 
- Value: 실제 값
- Metadate: 값에 대한 설명
- Version ID: 

#### S3 핵심 구성요소
1. Bucket
- S3 객체를 담는 최상위 저장 공간
- 이름 특징
    - AWS 계정 내에서 고유해야함
    - 일반적으로 소문자,숫자,하이픈을 사용함
    - 한 번 정한 이름은 다른 사람이 사용중이면 만들 수 없다.
    - 버킷은 특정 리전에 생성됨.
- 버킷은 실제 폴더가 아님.

2. Object
- 실제로 저장되는 데이터 단위

3. Key
- 버킷 안에서 객체를 구분하는 고유한 이름

##### 개인적인 생각
- Bucket은 domain address같고 
- Key는 URL 같음.

#### S3 사용이유
1. 제한 없이 확장 가능함.
2. 서버가 바뀌어도 파일이 유지됨.
3. 내구성과 가용성이 높음.

#### S3 주요 기능
1. Versioning
- 같은 key 파일을 다시 올려도 이전버전을 기억하는 기능
- Lifecycle과 같이 사용해서 오래된 버젼은 싼 곳에 최신 버젼은 비싼 곳에 저장하는 방식으로 할 수 있음.

2. Lifecycle Rule
- 오래된 객체를 더 저렴한 스토리지에 옮기는 기능

3. 스토리지 클래스 설정
- 접근 속도, 복구 속도에 따라서 필요한 스토리지 클래스를 사용

#### 사용처

1. 이미지 저장
2. 정적 웹사이트 배포

### RDS
- 클라우드에서 RDB를 쉽게 사용할 수 있도록 제공하는 완전관리형 서비스
- 초기 프로젝트일 경우 RDS를 세팅해서 개발 속도를 높이는 것이 좋을 경우도 있음. (이후에 EC2로 마이그래이션 하는 방식)
- 하지만 비싸기에 성공할 가능성이 높다고 생각하는 프로젝트 아니면 사용하지 않을 듯

#### 구성 요소
1. DB Engine
- 실제 데이터를 저장하는 SQL를 처리하는 데이터베이스 엔진

2. DB Instance
- 실제 DB엔진이 실행되는 서버 자원
- CPU+메모리+Network

3. Storage
- RDS에 저장되는 데이터들은 단순히 데이터베이스 로우만 저장하지 않음.
- IOPS : Input/Output Operation Per Second = 디스크가 1초에 처리할 수 있는 작업 횟수
- Throughput: 초당 전송가능한 데이터의 수

4. Endpoint
- 애플리케이션 RDS에서 접속할 수 있는 지점

#### 제공 기능
1. 자동 백업 
- RDS가 주기적으로 수행하는 관리형 백업
- 문제가 있다고 판단하면 자동으로 백업을 수행함.

2. Manual Snapshot
- 사용자가 원하는 시점에 직접 만드는 DB 스냅샷
- 스키마 변경, DB 엔진 업데이트 등 큰 변화 작업 전에 현재 상태를 보관하는 것. (그냥 수동 백업 아닌가?)

#### 실무 구성
1. Multi AZ 구성
- DB 장애상황에서 서비스 중단을 줄이기 위해서 다른 AZ에 대기 DB를 유지하는 구성
- 고가용성이지만 돈이 배로 들 듯

2. Read Replica
- DB 변경은 Primary DB에
- Read만 Replica에서 진행함. (보통 Read가 대부분이기에 효율적으로 자원을 활용할 수 있음.)

#### 주의 사항
1. RDS 백업 기능을 신뢰하지 말아라.
- 자동 백업이 제공되지만 실제 복구가 검증되진 않음.
- DB가 터졌을 때, 들어온 요청들은 백업해주지 못함. 그래서 이것을 고려하는 것도 중요함. -> Redis같은 인메모리 DB에 실패한 트랜잭션을 일시적으로 저장함

2. DB 연결수를 무한으로 늘리지 말아야함.
- DB에는 커넥션 풀이 있는데 이것보다 많이 연결할 수가 없음.
