    ### a. 지연시간 (Latency)
    
    - 출처 : https://aws.amazon.com/ko/what-is/latency/ +  DATA COMMUNICATIONS& NETWORKING WITH TCP/IP PROTOCOL SUITE
    - 요청된 리소스가 대상에 도달하는데 걸리는 네트워크 시간
    - 영향을 주는 요소들
        - 전송 시간 + 전파 지연 + 처리 지연 + 큐잉 지연 = 지연시간
            - 전송 시간(Transmission Time):  제한된 대역폭에 데이터를 넣어 전송하기에 발생하는 지연
            - 전파 지연(Propagation Delay): 물리적 거리 또는 통신 매질에 의한 지연
            - 처리 지연(Processing Delay): 네트워크 장비가 받은 패킷을 목적지에 전달하기 위해 발생하는 연산시간에 의한 지연
            - 큐잉 지연(Queuing Delay): 장비에 트래픽이 몰려 큐에 데이터가 쌓여 기다림으로 발생하는 지연
        - 지연 원인들
            - 전송 미디어 : 광섬유 네트워크와 무선 네트워크의 차이처럼 데이터를 전달하는 물질이 무엇이냐.
            - 네트워크 트래픽 이동거리 : 당연히 이동거리가 멀면 더욱 지연시간이 길어진다.
            - 네트워크 홉 수: 네트워크 장비에서 목적지까지 잘 전달하기 위해 내부연산을 함 (데이터를 받아 패킷 뜯어서 ip 확인 + ip table확인해서 해당 port로 전송) → 네트워크 장비를 많이 거칠 수록 지연시간이 길어짐.
            - 데이터 볼륨: 동시 데이터 볼륨이 크면 네트워크 디바이스에서 처리 용량이 제한되어 지연 시간이 늘어남
            - 서버 성능: 애플리케이션 서버 성능이 낮으면 당연히 응답이 느려지기에 지연시간이 늘어남.
    
    ### b. 지터 (Jitter)
    
    - 출처 : https://datatracker.ietf.org/doc/html/rfc3393 , https://www.cisco.com/c/ko_kr/support/docs/voice/voice-quality/18902-jitter-packet-voice.html
    - 지연 시간이 시간에 따라 불규칙하게 변하는 변동성
    - 발생 원인: 큐잉 지연(Queueing Delay) → 트래픽이 바뀌면 큐잉 지연도 바뀜.
        
        !image.png
        
    - 미치는 영향
        - 화면 멈춤 및 음성 튐 현상
        - 패킷 순서 뒤바뀜
    - 해결하기 위해 사용하는 기술: jitter Buffer
        - client에서 임시 저장소를 만들어서 들어오는 데이터를 바로 보여주지 않고 일정시간동안 모아서 정렬한 데이터를 보여줌. → 유튜브 보면 재생 바에 회색으로 표시하는 것이 이것으로 알고 있음.
    
    ### c. 패킷 손실 (packet loss)
    
    - 말 그대로 패킷이 사라진 경우
    - 원인
        - 네트워크 혼잡(Network Congestion): 네트워크 혼잡으로 인해 라우터의 Queue가 꽉차서 데이터가 들어오지 못한 경우 (Buffer Overflow)
        - 물리적 링크 오류 및 신호 간섭: 광케이블의 절단, 구리선의 감쇄 현상 등 통신선에 문제가 있어서 데이터가 소실되는 경우
        - 소프트웨어 오류: 네트워크 장비의 소프트웨어 오류로 인해 버그로 패킷이 유실되는 경우
    - 미치는 영향
        - 스트리밍 서비스의 하부 프로토콜 ( TCP vs UDP)의 설계 철학에 따라 다름
        - TCP 기반 서비스 (일반 VOD)
            - TCP는 신뢰성을 보장하는 프로토콜이기에 패킷 손실을 감지하면 다시 보내달라고 ARQ를 전송함.
            - 좋은 것처럼 보이지만 만약 패킷 하나가 소실되서 영상의 1프레임만 소실되어도 멈추고 해당 패킷을 받을 때까지 기다림. → 버퍼링(Buffering)
        - UDP 기반 서비스 (실시간 화상회의)
            - UDP는 신뢰성을 포기하여 재전송을 기다리지 않음.
            - 실시간 경기 볼 때 조금의 패킷 로스가 있어도 실시간으로 경기를 보는 것이 중요하니까 UDP는 실시간 영상송출에 적합함.
    - 해결하기 위해 사용하는 기술
        - 순방향 오류 정정 (Forward Error Correction)
            - packet loss가 발생해도 수신단에서 재전송 없이 원본 패킷을 복원함. → ARQ를 전송해 데이터를 받는 기술(Backward Error Correction)의 문제를 해결하기 위한 기술
        - 트래픽 셰이핑 및 QoS 우선순위 지정 (Traffic Shaping & Queueing)
            - 패킷에 우선순위를 정해서 네트워크 장비의 우선순위 큐에 저장하는 방식
            - 지연에 민감한 영상같은 패킷은 다른 패킷보다 우선순위가 높도록 설정

### RTP (Real-time Transport Protocol, 실시간 전송 프로토콜)

- IETF에서 제정한 실시간 미디어 전송을 위한 표준 프로토콜임
- UDP 위에서 동작하는 애플리케이션 계층
    - UDP의 장점인 실시간성을 중요하게 봐서 선택됨.
    - 하지만 패킷 내부에 순서와 시간정보를 넣어서 UDP의 단점을 극복함. → Buffering
- UDP port 중 짝수 port번호를 사용함.

#### 핵심 기능

1. 타임스탬프 동기화 (Time Synchronization)
    - 패킷마다 찍힌 타임스탬프(절대 시간)가 있어서 이를 통해 수신단에서 Buffering을 통해 Jitter 문제와 오디오, 비디오의 싱크문제를 해결함.
2. 번호를 통한 순서 정렬 (Sequence Numbering)
    - 패킷을 보낼 때 일련번호를 부여하여 패킷의 순서를 알 수 있도록 함.
    - 수신단에서 이를 보고 순서를 재정렬하고 손실된 패킷을 파악할 수 있음.
3. 페이로드 유형 식별 
    - 전송 중인 미디어 데이터의 압축 코덱 포멧이 무엇인지 명시함.
    - 이를 통해 수신단에서 어떤 디코더를 올려서 영상을 풀어야 할지 실시간으로 판단함.

#### 한계

- 제어 기능이 없음 → 그래서 이를 보완하는 제어프로토콜 RTCP와 함께 사용해야함.
- 보안에 취약함. → 보안을 추가한 SRTP(Secure RTP) 로 진화함.

#### 패킷 해더

```java
+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
|V=2|P|X|  CC |M|  Payload type |       Sequence Number         |
+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
|                           Timestamp                           |
+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
|           Synchronization Source (SSRC) identifier            |
```

### RTCP (Real-Time Transport Control Protocol, 실시간 전송 제어 프로토콜)

- UDP 기반 프로토콜
- RTP 다음의 짝수 port번호를 사용함.

#### 핵심 기능송 품질

- 전송 품질 피드백 (QoS Feedback): 수신 측이 겪고 있는 패킷 손실률, 지터, 왕복 지연 시간(RTT) 등의 통계 데이터를 송신 측에 주기적으로 피드백함.
- 미디어 스트림 간 동기화 (Inter-media Synchronization): 같은 세션 내에서 전송되는 서로 다른 미디어 스트림(예: 별도의 RTP로 전송되는 오디오 스트림과 비디오 스트림)의 절대적 시간 축을 맞춰 싱크를 일치시킴.
- 참여자 식별 (Session 참가자 관리): 세션에 참여 중인 소스들의 고유한 식별 정보를 제공하여 다자간 대화 등에서 누가 어떤 스트림을 보내고 있는지 관리함.

### RTSP (Real-Time Streaming Protocol, 실시간 스트리밍 프로토콜)

출처: https://datatracker.ietf.org/doc/html/rfc2326

- 사용자가 미디어 서버에 있는 영상을 재생하거나 멈추도록 지시하는 제어하는 프로토콜
- 유튜브를 볼 때 플레이어 하단의 재생, 일시정지 버튼을 누르는 동작같은 것들을 네트워크 프로토콜로 구현한 것
- port 번호 : TCP 554
- RTCP vs RTSP
    - RTCP: 전송 품질, 미디어 동기화 등 미디어의 품질 제어를 위한 프로토콜
    - RTSP: 미디어 서버를 제어하기 위함 프로토콜
- HTTP와 비슷하게 텍스트 기반의 구조 상태 코드 등 유사하지만 HTTP와는 다르게 stateful함.

### RTMP (Real-Time Messaging Protocol, 실시간 메세지 프로토콜)

- 출처 : https://ossrs.net/lts/en-us/assets/files/rtmp_specification_1.0-25a467618b92a3115bc97d4b0038b0ff.pdf
- 과거 어도비(Adobe) 사가 플래시(Flash) 플레이어와 미디어 서버 간에 오디오, 비디오, 데이터를 저지연으로 스트리밍하기 위해 개발한 **TCP 기반의 독점 프로토콜**
- port num: 1025

#### 연결 흐름

```java
[클라이언트 (인코더 / OBS)]                      [RTMP 미디어 서버]
         |                                             |
         | ---------- 1. Handshake (C0/C1/C2) -------> | (성공 시 커넥션 확정)
         | ---------- 2. connect (애플리케이션 연결) --> |
         | ---------- 3. createStream (스트림 생성) --> |
         | ---------- 4. publish (방송 송출 시작) ----> |
         |                                             | === (미디어 데이터 지속적 송출) ===
```

- TCP 기반의 안정성과 저지연 기본적으로 3-Way Handshake를 거치는 패킷 유실이 없는 신뢰성을 보장합니다. HTTP 스트리밍처럼 영상을 파일(청크) 단위로 쪼개고 저장하는 과정 없이, 연결된 파이프라인을 통해 미디어 데이터를 연속적인 스트림 형태로 실시간 밀어내기 때문에 초기 지연 시간이 3~5초 수준으로 상당히 낮음.
- **메시지 청킹(Chuncking) 메커니즘:** 네트워크에서 큰 비디오 데이터가 지나가느라 작은 오디오나 제어 명령 데이터가 뒤로 밀리는 정체 현상을 막기 위해, RTMP는 자체적으로 데이터를 '청크(Chunk, 기본 128바이트)'라는 작은 단위로 쪼개어 보냄. 하나의 연결(TCP 세션) 안에서 오디오, 비디오, 제어 신호 청크들을 잘게 교차(Interleaving)하여 전송함으로써 지터와 딜레이를 최소화함.
- 일반 시청자에게 영상을 전송하는 프로토콜로는 사장됨
- 하지만 방송인이 영상을 미디어 서버로 송출하는데 사용하는 프로토콜로는 아직 표준 프로토콜로 잘 사용됨.

## 3. 주제에 대한 생각

> 스트리밍 서비스에서 지연 시간, 지터, 패킷 손실이 사용자 경험에 미치는 영향을 설명하고, 버퍼링과 전송 방식 선택이 실시간성 및 안정성에 어떤 영향을 주는지 분석하시오.
> 
- 아무 기술도 적용되지 않고 순수하게 영상을 받아 버퍼링 없이 보여준다면
    - 지연시간에 의해 실시간 영상의 가치가 떨어짐.
    - 지터로 인해 영상이 중간에 갑자기 멈추고 영상과 오디오의 싱크가 맞지 않 현상이 일어남.
    - 패킷 손실로 인해 tcp기반이면 영상이 멈추고 , udp기반이면 영상 중간에 사라진 프레임이 발생함.
- 버퍼링을 통해서 지터와 패킷손실이 발생하였을 때 영상이 멈추는 것을 방지하여 사용자 경험(Qos)가 높아짐. 하지만 결국 영상을 미리 받아서 버퍼링을 하기에 실시간성은 떨어짐 → 즉 안정성을 위해 실시간성을 떨어트림.
- TCP 기반이면 패킷 손실을 매꾸기 위해 ARQ를 보내서 손실된 패킷을 받음. 버퍼링처럼 안정성은 올라가지만 실시간성이 떨어짐
- UDP 기반이면 패킷 손실은 그냥 무시함. 그래서 안정성은 떨어지지만 실시간성이 올라감.
