### Proxy 

- 클라이언트와 서버 사이에서 중계자 역할을 하는 네트워크 장치

#### 사용 이유
- 보안 강화: 클라이언트와 서버의 직접적인 연결을 막고 요청을 검사하거나 차단.
- 트래픽 최적화
- 접근제어
- 로깅/감시
- 익명성
- 정책 적용

#### 종류
- Forward Proxy: 클라이언트 보호, 우회, 익명성, 사내 정책 적용
- Reverse Proxy: 서버보호, 로드밸런싱, SSL/TLS 처리, 캐싱, 로그 기록

#### Forward Proxy
- 클라이언트 대신 외부 서버에 요청을 보내는 프록시
- 서버입장에서는 Forward Proxy가 요청한 것으로 보이기에 익명성을 보장함 (VPN)
- 클라이언트가 자주 요청하는 데이터를 캐싱함.

##### 예시
- 회사 인터넷 프록시
- 학교 인터넷 프록시
- 캐싱 프록시
- 제한 우회: 특정 네트워크 제한을 우회하는데 사용할 수 있음

#### Reverse Proxy
- 서버 대신 클라이언트 요청을 처리하는 프록시
- 실제 서버에 접근하지 못해서 보안이 강화됨 (Forward Proxy의 익명성과 같은 이유)
- 클라우드 개발자라면 이것이 Forward보다 중요할 듯.

##### 예시
- Nginx
- Apache HTTPD
- Envoy
- HAProxy
- CloudFront
- API Gateway

##### Reverse Proxy가 로드 밸런서와 같은 역할도 할 수 있는거 아닌가?

- 보통 한 서버가 리버스 프록시와 로드 밸런서 역할을 수행한다.
- 프록시는 중계가 주 역할이여서 로드 밸런싱은 부가적인 효과 (보안도 마찬가지)
- 로드밸런서는 요청을 서버에 전달하는 것의 비율을 처리하는 로드 밸런싱이 주 목적.
- 목적이 다르다고 생가하면 될듯



### VPN
- 여러 네트워크 장비를 거쳐서 통신하여 보안이 약할 수 있음.
- 특히 공용와이파이
- 공용 인터넷 위에 암호화된 가상의 터널을 만들어서 네트워크를 사설망처럼 안전하게 사용하는 기술 (터널링)
- 키파일을 탈취당하면 공격자가 내부망에 접근할 수 있게 되어버림.

#### 사용 이유
1. 보안성 강화
- 내용은 암호화하고 목적지는 VPN Server이기에 공용 와이파이에 연결해서 누가 패킷을 뜯어본다고 해도 알 수 있는 정보가 거의 없다.

2. 익명성 
- Forward Proxy이기 때문에 관련된 특성을 가지고 있음.
- 한국에서 정보를 요청하는데 VPN Server가 있는 위치에 맞게 응답이 오도록 할 수 있음.

#### 연결 방식
1. Full Tunnel
- 모든 트래픽을 항상 VPN으로 보내는 방식

2. Split Tunnel
- 사내망에 가야하는 트래픽만 VPN 가고 나머지는 일반적인 인터넷으로 내보내는 방식

#### 사용예시
1. 재택 근무자가 사내 git 접속 (Bastion Server, Jump Server)
2. 공용망에서 통신 암호화 하기 
- 의문 : 근데 이것은 HTTPS를 사용했으면 안해도 상관없는거 아닌가? 이미 패킷이 암호화 되서 스푸핑 해도 상관없지 않나? -> HTTPS는 해당 프로토콜만 보호하는데 VPN은 네트워크 터널링이기 때문에 다른 프로토콜도 암호화 하여서 보호할 수 있다.
3. LAN과 LAN을 연결하기 위해 Site-to-Site VPN Tunnel 형성 (회사 IDC - AWS)


### NAT

- IPv4의 주소 한계: 43억개의 주소를 가지고 있는데 인구만 해도 80억이고 한 사람이 가지고 있는 전자기기의 수가 늘어나면서 한계가 발생

- NAT Table을 만들어서 공유기의 port번호를 활용해서 사설망 ip를 공개 ip + port num과 목적지 ip를 매핑함.

#### Symmetric NAT
- 목적지가 다를 때 마다 사설망 IP가 같다고 해도 새로운 포트를 할당함.
- 매핑 독립성
- 보안 강화
- P2P 연결 제약
- 테이블 크기 증가

#### Cone NAT
- 사설 IP와 포트에 대한 NAT 매핑을 고정함.
- 외부 IP에서 매핑에 접근 가능함. (Symmetric과는 다르게 목적지가 달라도 포드가 같아서)

##### Full Cone NAT
- 송신 데이터 기반으로 NAT 테이블 생성
- 사설망에서 아웃바운드 요청한번만 하면 NAT Table에 매핑되어 이후 외부에서 접근가능
- P2P 통신, 온라인 게임, 화상통화

#### Restricted Cone NAT
- 내부 클라이언트가 아웃바운드 요청을 보낸 외부 IP(목적지)만 접근 허용
- Full Cone NAT에 비해 보안성이 높음.

#### Port Restricted Cone NAT
- 외부에서의 요청이 매핑된 목적지의 외부 IP + 포트 번호가 같아야만 접근을 허용함.
- 가장 엄격한 형태의 Cone NAT
- P2P 통신에서 추가적인 설정 필요함.

### 네트워크 프로토콜
- 네트워크 상에서 데이터를 주고 받는 규칙이나 절차
- TCP: 신뢰성 있는 데이터 전송
- UDP: 비연결성 프로토콜 
- ICMP: 네트워크 상태를 관리하기 위한 프로토콜 
- ARP: IP주소로 물리 주소를 알아내기 위한 프로토콜
- HTTP: 웹브라우저 - 서버간을 위한 프로토콜
- FTP: 서버-클라이언트 간 파일 전송 프로토콜
- SSH: 안전한 원격 접속 제공 프로토콜 
- SMTP: 이메일을 위한 프로토콜 

#### CIDR
- 네트워크 주소 설정 방식
- A,B,C 클래스로 나누어서 네트워크를 할당했음
- subnet mask로 network, host를 구분함.
- 설정할떄 네트워크 주소와 브로드캐스트 주소는 제외하고 호스트를 할당함.
- 이미 전공에서 주구장창 배운 내용이라 중요한 것만 정리함.
