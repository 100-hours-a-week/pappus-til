### ORM

- 자바의 객체와 데이터베이스 테이블을 자동으로 연결하고 변환해서 객체지향 코드로 데이터를 조작할 수 있게 하는 기술

- 객체는 객체지향으로 DB는 테이블 중심으로 설계-> 그 사이에 연결하는 역할
- SQL 중심으로 개발하다가 비즈니스 로직을 작성하는 것보다 SQL 매핑, 최적화하는데 시간이 더 오래걸린다.

자바와 RDB의 차이점
1. 상속과 다형성
- 자바: 클래스로 상송 기능이 지원된다.
- RDB: 상속의 개념이 없다.
2. 연관관계
- 자바 : 연관관계가 참조 관계이기에 단방향임.
- RDB : 외래키 + JOIN을 사용해서 연관지음. 관계를 설정하기에 방향이 양방향임.

3. 데이터 탐색 범위
- 자바 : 그래프 탐지
- RDB : SQL에 따라서 데이터 탐지가 상당히 넓게 가능함.

#### JPA

- 자바 객체와 관계형 데이터베이스를 매핑하고, 객체 단위로 데이터를 저장 및 조회할 수 있도록 해주는 표준 ORM 인터페이스

JDBC
- 기존에 자바랑 DB를 연결하기 위해 사용한 고대 유물
- 해당하는 데이터베이스에 쿼리를 전달할 수 있는 통로 (MySQL JDBC , MariaDB JDBC, Postgres JDBC)
- 개발자가 쿼리문을 직접 작성해서 DB에 연결해야 했음.

JPA
- 개발자가 직접 JDBC를 다루지 않고 중간에 ORM의 역할만 수행함.
- 엔티티를 JPA에 전달하면 알아서 쿼리문을 생성해서 JDBC를 통해 전송함.

#### Entity

```java
package kr.adapterz.jpa_practice.entity;

import jakarta.persistence.*;
import lombok.Getter;
import lombok.Setter;

@Entity
@Getter @Setter
public class User {
		@Id
    private Long id;
    private String email;
    private String password;
    private String nickname;

    protected User() {}

    public User(String email, String password, String nickname) {
        this.email = email;
        this.password = password;
        this.nickname = nickname;
    }
}

```

### 영속성 컨텍스트
-  JPA가 엔티티 객체를 관리하며, 동일 트랜잭션 내에서 변경 사항을 추적하고 자동으로 데이터베이스와 동기화하는 메모리 상의 저장소

- 애플리케이션 내부 메모리에 존재하며, 트랜잭션이 끝날 때까지 엔티티의 상태를 보관함.

- 트랜잭션이 커밋되는 순간, 영속성 컨텍스트에 기록된 변경 내역이 데이터베이스와 동기화

- EntityManager를 통해 접근함.

#### 특징

1. 1차 캐시
- DB와 WAS 사이의 cache
- 데이터를 두 번째 조회하면 빨라지도록 하는 역할.

2. 쓰기 지연 (Write-behind)
- 엔티티 인스턴스에 대한 쿼리를 바로 DB에 보내지 않고 1차 캐시에만 반영하고, 쿼리는 쓰기 지연에 넣어둠.
- flush할 때 DB로 모두 반영함.

3. 변경 감지
- 엔티티가 영속성 컨텍스트에 처음 들어올 때 엔티티의 상태를 복사해서 저장함.
- flush 전에, 스냅샷과 엔티티를 비교 다르면 DB에 Update함.

의문 : 굳이 이렇게 하는 이유가 뭐지? 그냥 쓰기 지연으로 충분하지 않나?

4. @Transactional
- 영속성 컨텍스트와 트랜잭션은 생명주기를 같이함.
- 다른 엔티티 매니저라도 같은 트랜잭션이면 동일한 영속성 컨텍스트 사용함.
- 이러하기에 Lost Update 현상 발생 

엔티티 상태
비영속 상태: 객체는 생성되었지만 영속성 컨텍스트에 관라 안됨 

영속 상태: 엔티티가 영속성 컨텍스트에 저장 관리되는 상태 (persist(entity))

 준영속 상태: 영속 상태였으나, 영속성 컨텍스트에서 분리된 상태, 영속성 컨텍스트가 닫히면 안에있는 엔티티는 준영속 상태 (detech(entity))
- 그럼 이건 그냥 공간만 차지하는 쓰레기인가? 바로 제거 대상이 되나?

삭제 상태: 삭제 예정으로 표시하여 DB에 제거를 요청함.(remove(entity))

#### 연관관계 매핑

1. 단방향 연관관계
- 하나의 엔티티에서만 다른 에티티를 참조해 관계를 맺는 방식
- 데이터베이스에서는 양방향만 가능하지만 객체는 단방향이 가능함.
- 설계를 단순화하고 불필요한 의존석 제거
- @ManyToOne, @OneToOne


2. 양방향 연관관계
- 두 엔티티가 서로를 참조해 양쪽에서 모두 관계를 탐색할 수 있도록 매핑한 방식
- @OneToMany, @ManyToMany

### 프록시와 지연로딩
프록시: JPA에서 지연로딩을 사용할 때, 실제 엔티티 대신 먼저 생성되어 전달되는 가짜 객체

즉시 로딩(Eager Loading): 연관된 모든객체를 즉시 조회함. 연관 엔티티를 LEFT OUTER JOIN으로 한 번에 조회함.

지연로딩: 객체를 불러올 때, 실제 조회를 하지 않고 프록시를 넣어둔다.
이후 프록시의 데이터가 필요할 경우 DB를 조회함.

지연로딩의 N+1 문제
- 프록시에 순차적으로 접근하는 코드가 있으면 프록시를 접근하는 쿼리문이 반복됨. (주 객체 조회 + 프록시 조회 * N = N + 1 ) 

해결방법
- Fetch join = Eager
- JPQL = 자바에서 SQL문을 작성
- 배치 사이즈 조절 = 페이징 처리
(Batch: 여러 개의 SQL문을 한 번에 모아서 DB로 전송해 처리하는 기능 -> flush함수를 부르면 발생하는 처리과정을 Batch라고 하는 듯)

- JPA는 엔티티를 생성할 때 리플렉션을 사용함.
- public 또는 protected로 존재해야 인스턴스화 가능
- 실무에서는 protected로 기본생성자를 제한하는 편. (실제 사용은 유효성 검증이 있는 생성자나 정적 팩토리로 제한하면 도메인 규칙을 지키면서도 JPA 요구사항을 만족시킬 수 있음.)
- final로 설정하면 바꿀수 없기 때문에 지연로딩이나 변경 감지기능 사용이 제한됨.


### 오늘의 한 줄 정리
 - ORM : 객체지향 특성과 관계형데이터베이스의 특성을 살리며 활용하기 위한 기술 -> 자바를 공부했는데 SQL문까지 다루기 귀찮은데? 해서 만들어짐.
 - JPA : 자바의 ORM 표준 인터페이스 -> ORM과 구분하기 힘드네 -> ORM은 기술명 , JPA는 그 기술을 사용하기 위한 명세 (찾아보니 구현체는 Hibernate이고 인터페이스가 JPA => 즉 비유하자면 List가 ArrayList로 생성되었다면 List는 JPA , ArrayList는 Hibernate. List는 명시된 함수를 사용만 할 수 있지 변경은 불가능. 함수 자체의 기능을 결정하는 것은 ArrayList , Hibernate)
 - Entity : 관계형 데이터베이스의 테이블과 매핑 시키기위한 객체 
 - 영속성 컨텍스트 : 엔티티를 관리하기 위한 곳으로 1차 캐시 , 쓰기 지연 장소 등이 있다. 
 - 연관관계 매핑 : 객체 간 관계와 관계형 DB의 테이블 간 관계를 매핑하는 것
 - Proxy : 지연로딩을 하기 위한 더미객체
